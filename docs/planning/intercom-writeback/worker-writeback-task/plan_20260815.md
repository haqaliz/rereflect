# Implementation plan — Worker write-back task

**Aspect:** `worker-writeback-task` (prd.md R3 + R5, worker side) · **Plan date:** 2026-08-15
**Branch:** `feat/intercom-writeback` · **Card:** `docs/planning/_card/card.md` (freeform)
**Spec:** `docs/planning/intercom-writeback/worker-writeback-task/spec.md`

## 1. Scope and boundaries

Build the core execution unit of the Intercom write-back: a Celery task that, given an
org and a list of feedback ids that just transitioned to `resolved`, appends a note to
each linked Intercom conversation and closes it. It is guarded (7 guards), idempotent
(DB-durable marker), honest about failures (recorded per-item, never raises, never flips
`is_active`), and visible on the Customer 360 timeline (one `intercom_writeback`
`FeedbackWorkflowEvent` per acted item).

**This aspect owns:** the task module, its tests, its registration (Celery `include` +
name-consistency test). **Worker-service only** — no backend-api code, no client code.

**Owned elsewhere (do NOT touch):**

| Piece | Owner |
|---|---|
| `IntercomClient.add_note` / `close_conversation` / `fetch_admin_id` + `IntercomNotFoundError` | `worker-write-client` aspect (spec says these are planned there; `src/clients/intercom.py` today has none of them — verified, only `search_conversations`) |
| `intercom_writeback_at` + 5 writeback columns (backend + worker mirrors, migration) | `db-config-model` aspect |
| Dispatch call sites (5) + `dispatch_intercom_writeback` helper | `dispatch-seams` aspect |
| Backend timeline fetcher `_fetch_intercom_writeback` in `customer_timeline_service.py` | **`dispatch-seams` aspect — DECISION D6** |
| Frontend card + `PATCH /writeback` config API | `frontend-writeback-card` / `config-api-routes` |

Sequence: after `db-config-model` and `worker-write-client`; before `dispatch-seams`.

## 2. Pinned contracts (decisions)

### D1 — Registered task name and dispatch payload (verbatim contract)

- **Task function:** `push_resolved_writeback` in `services/worker-service/src/tasks/intercom_writeback.py`.
- **Registered name (the string dispatchers send):**
  `src.tasks.intercom_writeback.push_resolved_writeback`
  (module `src.tasks.intercom_writeback` added to `celery_app.conf.include` — a task
  module missing from `include` is never imported by the worker, so `send_task` would
  raise `NotRegistered` in the worker — the beat-registration lesson, `celery_app.py:61-71`).
- **Dispatch contract (what `dispatch-seams` sends, quoted from its spec):**
  - Backend: `send_task("src.tasks.intercom_writeback.push_resolved_writeback", args=[org_id, items])`
  - Worker writers: `push_resolved_writeback.delay(org_id, items)`
  - `org_id` = int; `items` = `[{"id": <int feedback id>, "resolution_note": <str|None>}, ...]`.
    Exactly these dict keys — the task reads `item["id"]` and `item["resolution_note"]`.
- **Task signature:** `push_resolved_writeback(self, org_id: int, items: list) -> dict`.
  Decorator: `@shared_task(bind=True, max_retries=3, default_retry_delay=30, name="src.tasks.intercom_writeback.push_resolved_writeback")`.
- **Return contract:** `{"status": "ok", "processed": <int>, "results": [{"id": int, "status": str, "reason": str|None}, ...]}` — one entry per item; `status` is the per-item outcome (below). Celery result backend expiry (1 h) applies; the return is for tests/observability, not consumed by dispatchers.
- The task is **NOT beat-scheduled** — dispatched only via `send_task`/`delay`. No `beat_schedule` entry; do not add one.

### D2 — Per-item order of operations

For each item, strictly:

1. **Guard 1** — load `FeedbackItem` by `id` **and** `organization_id` (org-scoped; a wrong-org or missing id is `noop/not_found`).
2. **Guard 2** — `source == "intercom"` and a non-empty `source_metadata["conversation_id"]` → else `noop` (reason `not_intercom` / `no_conversation_id`).
3. **Guard 3** — `intercom_writeback_at` already set → `noop/already_written` (the re-resolve-after-reopen and retry-idempotency guard).
4. **Guard 4** — resolve the credential: token-paste `IntercomIntegration` row for the org first; if none, legacy `Integration(type="intercom", is_active=True)` OAuth row (source_events.py:190-227 OR-clause precedent — both paths, token-paste wins). Neither → `noop/no_connection`. (Note: for a writeback task the token-paste row is matched **by `organization_id` only** — it is a per-org row (`uq_intercom_integrations_org_id`), no workspace matching needed; the OAuth row is matched by `type == "intercom"` + `is_active`.)
5. **Guard 5** — writeback eligibility: token-paste row → `writeback_enabled` must be true, else `noop/writeback_disabled`. Legacy OAuth row → eligible by active connection (grandfathered — **DECISION D4**).
6. **Guard 6** — decrypt the token (see §5). Missing `LLM_ENCRYPTION_KEY` / decrypt failure → `error/missing_encryption_key`, recorded, **no retry**.
7. **Guard 7** — admin id: token-paste `admin_id`, else OAuth `config["admin_id"]`; if absent, `client.fetch_admin_id()` (GET /me). Absent + fetch failure → `error/no_admin`, recorded, **no retry**.
8. **Act** — `add_note(conversation_id, admin_id, body)` where body = `resolution_note` (trimmed, non-empty) or the default `"Marked resolved in Rereflect."`; then, when `writeback_action == "note_and_close"` (or the OAuth default, D4), `close_conversation(conversation_id, admin_id)`.
9. **Marker** — set `feedback_items.intercom_writeback_at = now` after the action completes (success **or** `already_closed`-style 404) — commit per item (§4.1).
10. **Row update** — token-paste row only: `last_writeback_at/status/error` (D3). OAuth row: nothing (no columns).
11. **Timeline event** — one `FeedbackWorkflowEvent(event_type="intercom_writeback")` for every item that reached the acting stage (D7).

### D3 — Marker semantics (`intercom_writeback_at`)

- **Set (terminal):** success (`ok`); 404-not-found close-or-note (`already_closed` — so a re-dispatch/retry skips via guard 3).
- **NOT set (re-runnable):** `noop` guards 1–5, `missing_encryption_key`, `missing_write_scope`, `no_admin` — the operator fixing scope/key/admin must be able to retry without a second dispatch.
- **Rolled back on retry:** a 429/5xx aborts the run; the session rolls back, so nothing from the aborted run persists (matches the hubspot precedent's `retrying`-is-rolled-back note, `test_hubspot_writeback_task.py:466-470`).
- Setting is a **per-item `db.commit()`** (not just flush) so an aborted mid-batch retry never duplicates notes for already-completed items (§4.1 — this is the one deliberate departure from the hubspot flush-only idiom, required by batch retry semantics).

### D4 — Legacy OAuth `Integration(type="intercom")` row (spec open question, resolved)

The OAuth row has **no** `writeback_*` columns and no `writeback_enabled` flag (verified: it is created at `integrations.py:1108-1121` with `config={integration_type, workspace_id, workspace_name, admin_id}` + `oauth_access_token`; worker mirror `models/__init__.py:167-186`).

- **Eligibility:** the `writeback_enabled` gate applies to the token-paste row only. When the resolved connection is the OAuth row, v1 treats it as eligible if `is_active` (grandfathered — every OAuth connection predates the writeback feature, so "off by default" was never expressible; the active connection is the operator's opt-in). **Flagged alternative:** treat OAuth rows as always `writeback_disabled`; rejected because the spec's own open-question clause ("if the connection is the legacy OAuth row, record status in the task log + timeline event only") is only meaningful if OAuth-path writebacks can proceed.
- **Action default:** `writeback_action = "note_and_close"` for OAuth rows (no column); token-paste rows use their column value; unknown/blank value on the token-paste row → fall back to `"note_and_close"` + log.
- **Outcome recording:** token-paste row → `last_writeback_*` columns (D8 statuses). OAuth row → **task log + timeline event only** (the timeline event is the durable record). Do not attempt any column write on the OAuth row.
- An org with **both** rows: token-paste wins (guard 4 order) and its `writeback_enabled` is authoritative.

### D5 — Retry shape

- Transient failures (`IntercomTransientError`: 429 and ≥500 per `intercom.py:78-84`): `integ.last_writeback_status = "retrying"` (token-paste row), `db.flush()`, then `raise task_self.retry(exc=exc)` — `max_retries=3`, `default_retry_delay=30` on the decorator. The `Retry` exception aborts the run (loop + session), and the whole payload is re-executed on retry; per-item commits + guard 3 make re-runs idempotent. **This is deliberate batch-retry semantics: abort-and-retry-the-whole-payload, never per-item scheduling.**
- **Must NOT retry:** `IntercomAuthError` (401/403), `IntercomNotFoundError` (404), `ValueError`/`InvalidToken` from decrypt (guard 6), `fetch_admin_id` failures (guard 7). All are recorded terminal outcomes.
- **No eager mode** anywhere in tests — `task_self.retry` is mocked with `side_effect=Retry()` and asserted called once, exactly like `test_hubspot_writeback_task.py:447-470`.

### D6 — Timeline fetcher ownership: `dispatch-seams`

The backend fetcher `_fetch_intercom_writeback` in `customer_timeline_service.py` is **backend code** and both specs group it with the backend dispatcher work (this spec's OQ; dispatch-seams lists it as in-scope with its own AC3). **Decision: `dispatch-seams` owns it.** This aspect's contribution is the exact event contract it must consume (D7). This plan adds **no** backend file.

### D7 — Timeline event contract (written by this task, read by dispatch-seams' fetcher)

One `FeedbackWorkflowEvent` per acted item (steps 8-11 in D2), mirroring the
`status_writer.py:157-168` shape:

```python
FeedbackWorkflowEvent(
    feedback_id=item.id,
    organization_id=org_id,
    actor_id=None,                       # system-driven, status_writer precedent
    event_type="intercom_writeback",
    old_value=None, new_value=None,      # metadata carries everything
    metadata_={
        "source": "intercom",
        "action": "note_and_close" | "note_only",
        "note_sent": bool,               # True iff add_note succeeded or was 404-idempotent
        "closed": bool,                  # True iff close succeeded / 404 (already closed)
        "reason": str | omitted,         # missing_encryption_key | missing_write_scope |
                                         # no_admin | already_closed | not_found
    },
    created_at=datetime.utcnow(),
)
```

- **Written for:** every item that passes guards 1–5 (reaches decrypt/act stage) — success **and** recorded failures (`missing_encryption_key`, `missing_write_scope`, `no_admin`, `already_closed`). This is what makes the OAuth path's outcomes durable.
- **NOT written for:** guards 1–5 noops (`not_found`, `not_intercom`, `no_conversation_id`, `already_written`, `no_connection`, `writeback_disabled`) — pure returns, no noise; and not for the aborted retry run (rolled back).
- `metadata_` key names are **contract** — dispatch-seams' fetcher mirrors `_fetch_status_changed` filtering `event_type == "intercom_writeback"` and describing from `metadata_`; do not rename keys.

### D8 — Row status vocabulary (token-paste `last_writeback_*`)

| Outcome | `last_writeback_status` | `last_writeback_error` | Marker | Retry |
|---|---|---|---|---|
| Success | `ok` | `None` | set | — |
| 401/403 | `error: missing_write_scope` | str(exc)[:500] | not set | no |
| 404 note/close | `noop: already_closed` | str(exc)[:500] | set | no |
| Missing key / decrypt fail | `error` | `missing_encryption_key` (or `token_decrypt_failed`) | not set | no |
| No admin | `error: no_admin` | str(exc)[:500] | not set | no |
| 429/5xx | `retrying` (rolled back on abort) | str(exc)[:500] | not set | yes, ≤3 |

- **`is_active` is NEVER touched** — soft-pause precedent (`hubspot_writeback.py:158-168`): the flag is owned by the read-sync task (`intercom_sync.py`).
- Batch of N items → last-writer-wins on the org row (an `ok` item followed by a scope-error item leaves `missing_write_scope` — the most recent failure is what the operator sees; per-item detail lives in the timeline events + results dict).

## 3. Client dependency contract (what `worker-write-client` must deliver)

The task imports from `src.clients.intercom` — today these **do not exist** (verified: `intercom.py` has only `search_conversations`/`_normalize`):

- `add_note(conversation_id: str, admin_id: str, body: str)` — POST `/conversations/{id}/reply`, body `{"message_type": "note", "type": "admin", "admin_id": ..., "body": ...}`.
- `close_conversation(conversation_id: str, admin_id: str)` — POST `/conversations/{id}/parts`, body `{"message_type": "close", "type": "admin", "admin_id": ...}`.
- `fetch_admin_id() -> str` — GET `/me`, returns `data["id"]`; raises `IntercomAuthError` on 401/403 (per worker-write-client spec).
- `IntercomNotFoundError` — a new distinct 404 exception. **Critical ordering note for the sibling aspect:** the current `_handle` (intercom.py:85-86) falls through `>= 400` to `IntercomAuthError`, so a 404 must be intercepted by a `resp.status_code == 404` branch **before** the `>= 400` catch-all. Without this, a closed conversation is misclassified as an auth error and recorded as `missing_write_scope` — the exact "honest failure" lie this feature exists to prevent.
- Transport injection stays as-is (`transport=` param) so client tests use `httpx.MockTransport`.

The task uses these via the `IntercomClient(token)` context manager; tests inject a `MagicMock` (hubspot idiom).

## 7. Edge cases & error handling

1. **All 7 guards** — see D2/D8; each returns `{"id", "status", "reason"}` and never calls the client (guard 7's `fetch_admin_id` excepted).
2. **403/401** — `missing_write_scope` on the row (token-paste), `is_active` untouched, marker unset, event with `reason="missing_write_scope"`. Never auto-disable (PRD R2 risk mitigation).
3. **404** — note-404 and close-404 both `noop/already_closed`; close-404-after-note counts as `closed=True` (idempotent-by-404); marker set so re-runs and re-resolves skip.
4. **429/5xx** — `task_self.retry` (≤3, delay 30), whole-payload abort-and-retry; per-item commits guarantee no duplicate notes for items completed before the abort (this is the crash-window fix, PRD R5 risk).
5. **Batch isolation** — only the deliberate `Retry` propagation aborts the run; auth/not-found/missing-key/no-admin failures are recorded and the loop continues.
6. **Marker semantics** — set on `ok` + `already_closed` only; never on config/auth failures (those must stay re-runnable); re-resolve after reopen is `already_written` (PRD R4 risk).
7. **Never raises** — the body only raises `task_self.retry(...)` (a `Retry` subclass); every IntercomError + decrypt failure is caught and recorded. **Decrypt hardening:** catch `ValueError` (missing key, hubspot precedent) **and** `cryptography.fernet.InvalidToken` (key changed — a permanent operator config error, must not escape and must not retry; reason `token_decrypt_failed`). This is a deliberate extension of the hubspot precedent, which predates the never-raises batch contract.
8. **No tokens in logs** — log org_id / feedback id / conversation outcome only (hubspot R3 rule).
9. **`Retry` on a failed item does not lose the batch** — the retry re-executes the full payload; guards 1–3 + per-item commits make completed items noops (`already_written`/`already_closed`).
10. **Malformed payload items** — an item without `id` (or non-int) is recorded `error/invalid_payload` and skipped, never raising; the batch continues.
11. **Legacy OAuth decrypt failure / stale token** — `error/missing_encryption_key` (or auth error) recorded in task log + timeline event only; soft-pause; no cascade (PRD R6 risk).
12. **Last-writer-wins row status** within a batch — documented in D8; per-item truth lives in timeline events + results.

## 10. Spec ambiguities flagged

1. **Legacy OAuth eligibility (spec OQ, guard 5).** Spec pins outcome-recording for OAuth rows ("task log + timeline event only") but not whether OAuth-only orgs can write back at all. **Decided (D4):** OAuth rows are eligible when active (grandfathered; `writeback_enabled` gate applies to token-paste rows only). Alternative — OAuth rows always `writeback_disabled` — rejected because the spec's OQ clause then describes an unreachable case.
2. **`_body` signature.** Spec writes `_body(task_self, db, org_id, payload)` (db injected) while naming `hubspot_writeback.py` (which opens its own session) as precedent. **Decided:** follow the spec's literal signature — db injected, wrapper owns `get_db_session()`, per-item commits inside the body.
3. **Per-item commit vs hubspot flush-only idiom.** Required for batch-retry idempotency (a mid-batch `Retry` rolls back flush-only writes → duplicate notes on retry). **Decided:** commit per item; flagged in code + §4.1.
4. **Timeline events for guard noops.** Spec says guards are "recorded noop/skipped" but doesn't say where. **Decided (D7):** guards 1–5 write no timeline event (pure returns); only acted outcomes (success + recorded failures) do. Guard noops are visible in the results dict + task log.
5. **`fetch_admin_id` transient (429/5xx).** Spec pins guard 7 as no-retry `error/no_admin` for any fetch failure, including transient. **Decided:** follow the spec (no retry) — a missing admin is an operator-config problem, not an upstream blip; flagged as a possible future refinement (retry transient `/me`).
6. **Timeline fetcher ownership.** Both this spec and dispatch-seams list `_fetch_intercom_writeback`; dispatch-seams even has AC3 for it. **Decided (D6):** dispatch-seams owns it; this plan supplies the event contract it consumes.
7. **`writeback_enabled` for OAuth rows** — see #1; also note the config API (`config-api-routes`) may 404 for OAuth-only orgs (R7 "404 when no connection") — that route's semantics are that aspect's call; this task is consistent either way.
