  1. `workflow_service.py` — after `dispatch_status_webhooks` (:78), add
     `dispatch_intercom_writeback` with the pinned signature:
     ```python
     def dispatch_intercom_writeback(
         db: Session,
         organization_id: int,
         changed_pairs: List[Tuple[FeedbackItem, str]],
         resolution_note: Optional[str] = None,
     ) -> None:
         """Enqueue the intercom_writeback task for changed Intercom-sourced
         items that transitioned to ``resolved``.

         Mirrors dispatch_status_webhooks: consumes the apply_status_change
         return value, fire-and-forget. ``fb.workflow_status`` is the NEW
         status because apply_status_change mutates the item before returning.
         NEVER raises — get_celery_app is imported lazily so an ImportError
         (worker-like context) is swallowed like any other enqueue failure.
         """
         try:
             items = []
             for fb, _old in changed_pairs:
                 if fb.source == "intercom" and fb.workflow_status == "resolved":
                     items.append({"id": fb.id, "resolution_note": resolution_note})
             if not items:
                 return
             from src.background.celery_client import get_celery_app

             get_celery_app().send_task(
                 "src.tasks.intercom_writeback.push_resolved_writeback",
                 args=[organization_id, items],
             )
         except Exception as exc:
             logger.warning(
                 "workflow_service: failed to enqueue intercom writeback for "
                 "org=%s items=%s: %s",
                 organization_id, [i["id"] for i in items], exc,
             )
     ```
     (module needs `logger = logging.getLogger(__name__)` — add if absent).
  2. `workflow.py` `change_status` — insert immediately after the
     `dispatch_status_webhooks` try/except (:183-190), before the `if updated > 0`

     ```python
         dispatch_intercom_writeback(
             db, current_org.id, status_changes, data.resolution_note,
         )
     except Exception:
         pass
     ```
     and add `dispatch_intercom_writeback` to the existing import from
     `src.services.workflow_service` (:20-24). Note the call-site variable is
     `status_changes` (= the `apply_status_change` return, :160-167).
  3. `public_api.py` bulk (`public_bulk_update_feedback`) — inside the best-effort

## Edge cases & error handling

- **Never-raise contract (AC2):** the backend helper swallows everything (`send_task`
  failure, `get_celery_app` ImportError) with a `logger.warning`; call sites add the
  same try/except the webhook dispatch uses. Worker writers dispatch directly (no
  wrapper needed — `.delay()` on a task object cannot raise for import reasons since
  the import is module-level and loud).
- **Empty `changed_pairs`:** `items == []` -> early return, no `send_task` (this is
  also the same-value no-op case at the backend: `apply_status_change` never includes
  unchanged items, :38-39).
- **Non-Intercom source / non-resolved:** filtered out in the helper; never dispatched.
- **Same-value no-op at worker writers:** guarded explicitly with
  `old_status != new_status` (these writers mutate unconditionally — without the
  guard a re-save would dispatch).
- **Mixed batch (bulk PATCH with intercom + email ids):** only intercom items land in
  the payload; one `send_task` per request (batched), not per item.
- **`resolution_note=None`:** payload carries `None`; the task body falls back to the
  default note text ("Marked resolved in Rereflect."). Never `""` — a `None` note from
  the worker writers and an omitted note from the backend both serialize to `null`.
- **The dispatcher never touches `intercom_writeback_at`** — the marker is the task's
  (sibling) concern; this aspect only enqueues.
- **Pre-commit worker dispatch race:** benign — the task body reads source /
  `source_metadata.conversation_id` / marker / integration row, never `workflow_status`
  (see decision log).
- **Broker down / task unregistered:** backend `send_task` failure is logged and the
  request succeeds (fire-and-forget, matches webhook/CRM writeback behavior). The
  name-consistency test + the sibling's AC6 guard the "silently never fires" class.
