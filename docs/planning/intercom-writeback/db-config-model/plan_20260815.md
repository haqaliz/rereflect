## 6. Edge cases & error handling

- **Existing rows**: `writeback_enabled` + `writeback_action` are `NOT NULL`, so the
  migration's `server_default` is mandatory — PostgreSQL refuses to add a NOT NULL
  column without a default to a populated table. Backfill semantics: every existing
  org is off (`false`) with action `note_and_close` — matches prd R1/OQ1 (off by
  default, no surprise mass-closes).
- **Existing feedback rows**: marker stays NULL — transitions before enable never
  dispatch (prd "Honest limits").
- **Downgrade**: drops exactly the six new columns; siblings untouched. Order of
  drops within a table is irrelevant, but keep the paired add/drop names exact.
- **SQLite vs PG**: boolean `server_default='false'` stores as literal text `"false"`
  on SQLite and real `false` on PG — migration tests must assert `in (False, 0, "false")`.
- **Type drift**: `DateTime(timezone=True)` is the spec's "timestamptz". If a naive
  `DateTime()` sneaks into one side, the new type-parity test fails — that is
  intentional.
- **Parity scope**: the existing parity test compares *names only*; the new
  `test_writeback_column_types_match` closes the "including types" gap (AC4) for the
  columns this aspect adds, without risk of unrelated pre-existing drift breaking CI.
- **Alembic heads**: if `down_revision` is wrong or stale, `alembic heads` prints ≥2
  heads and CI fails — the migration file's `down_revision` is pinned to
  `'3cb9a0d1456b'`.
- **No Redis, no backfill, no status-pinning**: explicitly out of scope (spec
  "Out of scope"); nothing in this aspect touches Redis or adds DB CHECKs
  (action values are Pydantic-validated in the config-API aspect R7).

## Spec ambiguities flagged

1. **timestamptz vs precedent's naive `DateTime`**: the spec explicitly says
   *timestamptz* for `last_writeback_at` and `intercom_writeback_at`, but the CRM
   precedent (`hubspot_integration.py:41`, `salesforce_integration.py:43`) uses plain
   `DateTime` (naive). This plan follows the **spec** (`DateTime(timezone=True)` in
   models, `sa.DateTime(timezone=True)` in the migration, mirrored identically in the
   worker). If the reviewer prefers strict precedent parity, swap all three places to
   naive `DateTime` — but the parity type-test will then enforce that choice
   consistently.
2. **`last_writeback_status` length**: spec says `String(64)`; hubspot/salesforce use
   `String(50)`. Plan follows the spec (64). Ensure the worker mirror matches.
3. **env.py registration**: `FeedbackItem` is registered, `IntercomIntegration` is not.
   Resolved: hand-write the migration (matches latest head style) **and** add the
   `IntercomIntegration` import to `env.py` so the metadata includes both tables.
4. **`writeback_action` server_default**: the spec says "not null, default
   `note_and_close`" without spelling out `server_default`; it is required for the
   NOT NULL constraint on existing rows and is included in the plan.
5. **Parity "including types"**: the existing parity test compares names only; the
   plan adds a targeted type-equality check for the six new columns to satisfy AC4
   without risking unrelated pre-existing drift.
