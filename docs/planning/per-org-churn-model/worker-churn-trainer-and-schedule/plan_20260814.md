## 2. Implementation phases (strict TDD)

### Phase 1 — RED: task module scaffold + beat entry test

- **Goal**: beat entry registered; task module importable without sklearn.
- **Files**: `celery_app.py`, `test_churn_classifier_training_tasks.py`
- **Steps**:
  1. Test: `celery_app.conf.beat_schedule` has `retrain-churn-classifier-weekly` →
     `src.tasks.churn_classifier_training.retrain_all_orgs` at **06:00 UTC Mondays**,
     ordered before `retrain-classifier-weekly` (06:30) and after
     `refit-global-calibration-daily` (03:00) / `refit-churn-calibration-weekly` (07:45 is
     *after* — so assert ML 06:00 < classifier 06:30, and document that the incumbent
     refit at 07:45 lands one week before the challenger evaluates it; add a comment in
     celery_app.py explaining the ordering intent).
  2. Test: the task module has no module-level sklearn/numpy import
     (`test_no_module_level_sklearn_import` convention).
  3. Scaffold the task file with `retrain_all_orgs` as a `@shared_task(name=...)`
     plain placeholder and stub `retrain_org` — RED on the ordering test first (no entry yet).
- **Validation**: ordering test RED → add the beat entry → GREEN.
- **Commit**: `test(worker): RED — churn classifier refit beat entry + ordering`

### Phase 2 — GREEN: retrain_org (promote path)

- **Goal**: per-org training with M5.2-identical promote semantics.
- **Files**: `churn_classifier_training.py`, `test_churn_classifier_training_tasks.py`
- **Steps**:
  1. `retrain_org(org_id, db)`: Redis advisory lock `lock:classifier_refit:churn:{org_id}`;
     labels via the core's `fetch_churn_rows` (+ the calibrator's `source != 'auto_suggested'`
     filter and 180-day window); features via `build_feature_vector`.
  2. Incumbent: load the org's active calibrated model (org → global → identity, the
     `calibration_refit`/`probability_updater._load_active_model` chain) and wrap it as
     the injected `incumbent_predict` (its `churn_risk_component`-based p over the same
     holdout).
  3. `evaluate_churn(...)`; on `promoted`: train final artifact on all rows, deactivate
     prior active `is_active` row, **`db.flush()` before INSERT** (partial unique index
     `uq_org_classifier_one_active`), INSERT `is_active=True`, write the
     `org_classifier_eval_runs` row, single `db.commit()`.
  4. Hold: re-read `churn_autopromote_hold` row-locked in the same transaction; held →
     `decision='held'` eval run with real delta/n, no promote.
  5. All class-imbalance/single-class outcomes → `skipped` with note (never raise).
- **Validation**: promote/retain/skip/held paths green; active-invariant across repeated
  refits; flush-before-INSERT test (clone `test_promote_flushes_deactivation_before_inserting_new_active_row`).
- **Commit**: `feat(worker): churn classifier retrain_org + promote with hold (TDD)`

### Phase 3 — GREEN: retrain_all_orgs + purge + lock behavior

- **Goal**: full sweep with isolation and cleanup.
- **Steps**: `retrain_all_orgs()` loops orgs with trainable labels, per-org try/except +
  rollback, tallies `{trained, promoted, skipped, held}`; lock miss → `{"skipped": True,
  "reason": "locked"}`; folds `purge_old_churn_classifier_models()` (inactive + fit_at <
  90 days) after the loop.
- **Validation**: per-org isolation (one org's exception doesn't stop the sweep); purge
  boundaries; lock acquire/release.
- **Commit**: `feat(worker): churn classifier sweep + purge + lock (TDD)`

## 6. Edge cases & error handling

- OrgAIConfig columns absent (aspect 5 migration not yet applied) → getattr-defensive,
  treat as `off` (no crash) — M5.2 `getattr` convention.
- Empty label set → skip; single-class → skip; corrupt incumbent artifact → fall back to
  identity, never raise.
- Never import backend-api (worker image constraint); core imported lazily.

## 7. Agent execution notes

- **Plan amendment (2026-08-14, from the gate-study verdict):** the study's honest-limits
  finding answered PRD OQ2 — at the 200-label crossover, only 57% of pooled simulated
  orgs cleared the +0.02 macro-F1 bar on a *single* run (high variance). Therefore the
  churn head's promotion rule is **consecutive-runs**: promote only when the challenger
  clears +0.02 on two consecutive weekly refits (with `decision` recorded per run:
  `promoted_candidate` then `promoted`). The autopromote hold must clear both runs'
  state. This deviates from M5.2's single-run rule deliberately and must be pinned by
  tests (e.g. clear-once-then-degrade → never promotes).
- Checkpoint after Phase 1: confirm the beat ordering intent with the user if the
  06:00 slot collides with anything else in the schedule (currently free).
- Sequencing: run after aspect 3; can run in parallel with aspect 5's migration work,
  but the task must be column-defensive until the migration lands.
