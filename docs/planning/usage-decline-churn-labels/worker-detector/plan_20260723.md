## 1. ⚠️ Placement correction — the spec is WRONG about where this hangs

`./spec.md` says to mirror "the M3.2c post-commit drain seam (`:659-681`)". **Do not hang the
detector there.** Verified execution order inside `recompute_usage_scores`
(`services/worker-service/src/tasks/usage_metrics.py`):

| Step | What | Line |
|---|---|---|
| 1 | score / trend `db.commit()` | `:655-657` |
| 2 | M3.2c drain seam — automation trigger evaluation | `:667-681` |
| 3 | **`_write_usage_history_snapshots` + `db.commit()` — SEPARATE transaction, at the very end** | `:693-694` |

**Today's snapshot row does not exist until step 3.** A detector at step 2 computes streaks against
history that is missing the current day — permanently one day stale. The resulting bug would present
as an off-by-one in the sustain window and would be hunted in `qualifying_streak`, which would be the
wrong place to look.

**Correct placement: after step 3, in its own transaction**, gated on the snapshot write having
succeeded.

**Useful interaction, document it:** the snapshot write is wrapped in `try/except` that logs and
continues (`:695-702`), leaving `snapshot_written = 0`. When it fails, today's row is absent — which
the core's **calendar-gap rule reads as a broken streak**, so the detector goes quiet rather than
computing a streak across a hole. The conservative rule and the failure mode agree. Prefer skipping
the detector outright when `snapshot_written == 0`, and log that you did.

## 3. Implementation Phases

### Phase 1 — Detector skeleton + mode gate

- **Goal:** `detect_usage_decline_labels(org_id, db, ...)` exists and respects the three modes.
- **Files:** `services/worker-service/src/services/usage_decline_label_detector.py` (new);
  tests in `services/worker-service/tests/test_usage_decline_label_detector.py`.
- **RED first**, one test per mode:
  1. `mode='off'` → returns immediately, writes nothing, **performs no history query**
     (assert via a session spy / query counter, not by inspecting return values).
  2. `mode='shadow'` → evaluates fully, logs a would-suggest count, writes **zero**
     `ChurnLabelSuggestion` rows.
  3. `mode='active'` → writes suggestions.
- Read the mode via the worker's mirrored `OrgAIConfig`. NULL/unrecognized → treat as `'off'`
  (defence in depth, matching how the sibling classifier modes resolve).
- Read `sustain_days` from `usage_churn_label_config`, defaulting to 7 when the JSON is NULL or the
  key is absent.
- **Commit:** `feat(usage-decline-churn-labels): detector skeleton + mode gate`

### Phase 2 — Batched history load

- **Goal:** Load the streak window for all of an org's customers in **one** query.
- **RED first:** assert the number of history queries does **not** scale with customer count
  (e.g. 50 customers → a small constant number of queries).
- Mirror `_load_trend_baselines` (`usage_metrics.py:279-338`): one SELECT scoped to the org and the
  date window, grouped in Python. **Never query per customer.** The composite index
  `ix_customer_usage_history_lookback (organization_id, customer_email, snapshot_date)` exists for
  exactly this shape.
- **Window:** fetch `sustain_days` **calendar days** of rows (not "the last N rows"), so the core's
  gap detection can see holes. This is the point flagged in the `detector-core` plan §7.
- **Commit:** `feat(usage-decline-churn-labels): batched streak-window history load`

### Phase 3 — M3b outage guard (BEFORE any write)

- **Goal:** An instrumentation outage suppresses the run instead of flooding the queue.
- **RED first:**
  1. Org where >25% of eligible customers qualify, population ≥ min → **zero** rows written **and**
     a warning recorded with the counts.
  2. Same qualifying share in a tiny org (population < min) → suggestions **are** written.
  3. Exactly at the threshold → **not** suppressed (strict `>`, pinned in the core).
- Compute `qualifying` and `eligible` for the whole org, call `outage_suspected(...)` from the core,
  and **return before writing anything** when it trips.
- **The suppression must be loud** (house rule: no silent caps). Log the counts and the reason.
- **Commit:** `feat(usage-decline-churn-labels): population-level outage suppression`

### Phase 4 — Suggestion write + denials

- **Goal:** Qualifying customers become pending suggestions, idempotently.
- **RED first**, one test per rule:
  1. Qualifying 7-day `sharp_decline` streak → exactly one row, `provider='usage_decline'`,
     expected key, `suggested_churned_at == customer_usage.last_active_at`.
  2. **Run the detector twice on the same unchanged streak → still exactly one row** (idempotent via
     the natural key). This is the single most important test in the aspect.
  3. `last_active_at IS NULL` → no suggestion (deny; never substitute a fallback date).
  4. Customer already has an active `CustomerChurnEvent` → no suggestion.
  5. Cross-org isolation: org A's history never yields a suggestion for org B.
  6. Per-run cap: cap+N qualifying → exactly cap rows, dropped count **logged**.
- Reuse the shipped semantics from
  `services/worker-service/src/services/churn_suggestion_harvester.py`:
  `_existing_suggestion_row` (`:48-59`), `_has_active_churn_event` (`:62-79`), and the
  `db.begin_nested()` + `IntegrityError` → `skipped_existing` race backstop (`:142-161`).
  **Reuse the pattern; do not edit that module** — it is the CRM path and must not regress.
- Build `evidence` via the core's `build_evidence` — **do not** hand-roll the dict; the key names are
  a contract consumed by `../frontend-settings-and-evidence/`.
- **Commit:** `feat(usage-decline-churn-labels): write usage-decline suggestions`

### Phase 5 — Wire into `recompute_usage_scores`

- **Goal:** The detector runs daily, in the right place, and cannot break the parent task.
- **Files:** `services/worker-service/src/tasks/usage_metrics.py`
- **RED first:**
  1. **Ordering:** the detector is invoked **after** the snapshot commit. Assert a regression fails
     loudly — use the in-`side_effect` assertion technique M3.2c used
     (`services/backend-api/tests/test_usage_trend_trigger_seam.py` is the reference for the shape).
  2. **Isolation:** an exception raised for one org does not prevent other orgs being processed and
     does **not** fail `recompute_usage_scores`.
  3. `snapshot_written == 0` (snapshot write failed) → detector skipped, and the skip is logged.
- Follow the drain seam's `try/except` + `logger.error(..., exc_info=True)` idiom (`:672-681`)
  exactly; import the detector lazily inside the block, as that seam does.
- **Commit:** `feat(usage-decline-churn-labels): run detector after the daily snapshot commit`

## 6. Edge Cases & Error Handling

| Case | Required behaviour |
|---|---|
| Org has no `OrgAIConfig` row | Treat as `'off'`; no queries, no writes |
| `usage_churn_label_config` NULL | `sustain_days` defaults to 7 |
| Snapshot write failed this run (`snapshot_written == 0`) | Skip the detector, log the skip |
| Customer has a gap in history | Core breaks the streak → no suggestion (conservative, correct) |
| `last_active_at IS NULL` | Deny |
| Suggestion already exists (same natural key) | Skip, not an error |
| Two sources suggest the same customer | Existing `_has_active_churn_event` + confirm-time collision handling resolve to skipped — **assert it, don't assume it** (PRD R7) |
| Multi-tenancy | Every query scoped by `organization_id`; assert cross-org isolation |
