## 1. The contracts this aspect consumes (already fixed)

**Settings API (shipped in `config-and-migration`):** `GET/PATCH` on the AI settings surface now
carry `usage_churn_labels_mode` (`off|shadow|active` — validated server-side; `auto` → 422) and
`usage_churn_label_config` (`{sustain_days: int in [1,90]}`).
- Frontend client: `services/frontend-web/lib/api/ai-settings.ts` — `AISettings` (`:11`) and
  `AISettingsUpdate` (`:24`) already list `sentiment_provider` + the three `*_classifier_mode`
  fields. Add the two new fields alongside them.

**Evidence payload (frozen by `detector-core`'s `build_evidence`):**
```
{ trend_state, trend_pct, baseline_active_days_14d, current_active_days_14d,
  streak_days, streak_start_date, last_active_at, snapshot_series: [{date, active_days_14d}] }
```
All dates are ISO strings. `trend_pct` may be `null`.

### Phase 4 — Settings card (opt-in + honesty + precision read-out)

- **Files:** new `components/settings/UsageChurnLabelsCard.tsx`; mount it where the classifier-mode
  controls live — `components/settings/AISettingsGeneral.tsx` (the component that already renders
  `urgency_classifier_mode` / `category_classifier_mode`). Follow that file's control pattern
  exactly (mode select bound to `AISettingsUpdate`, saved through the existing settings mutation).
- **Controls:**
  - Mode: `off | shadow | active`. Explain shadow ("evaluate and show what would be suggested,
    write nothing").
  - `sustain_days` numeric input, client-validated to `[1,90]`; surface the API 422, don't swallow.
- **Honest-limits copy (PRD M6 must-have — assert it's in the DOM):** state the ~12-16 day warm-up,
  the extra `sustain_days` window, that **customers below the ≥5 active-day baseline floor can never
  produce a suggestion**, and that only *recently*-declining customers are visible (a long-departed
  customer never appears). An operator who enables this and sees nothing must learn why *here*.
- **Precision read-out:** confirmed / rejected / pending counts for `provider='usage_decline'`.
  - **Data source decision (spec open question):** prefer extending an existing payload over a new
    endpoint. Check whether the AI-settings GET or an existing analytics/readiness response can
    carry three integers; it is a `GROUP BY status` over a table already indexed by `(org, status)`.
    If nothing fits cleanly, fall back to querying the existing
    `GET /api/v1/customers/churn-suggestions?provider=usage_decline&status=...` counts client-side
    (three cheap calls or a `page_size=1` total-read per status). **Pick one, note it in the
    commit, do not invent a new backend endpoint in this frontend aspect** — that would belong in a
    backend aspect and expand scope.
  - `last_detection_at` / `last_detection_status` incl. the M3b suppression state **only if
    `worker-detector` surfaced it**; if that data isn't exposed yet, render the precision counts and
    leave a clearly-marked TODO rather than fabricating a field.
- **Validation:** `npm run test -- UsageChurnLabels` ; `npm run lint` ; `npx tsc --noEmit` clean.
- **Commit:** `feat(usage-decline-churn-labels): AI settings card for usage churn labels`

## 6. Edge Cases & Error Handling

| Case | Behaviour |
|---|---|
| `evidence` null/empty on a `usage_decline` row | Fallback text — but the detector always sends evidence, so this indicates a bug; render gracefully, don't crash |
| `trend_pct` null | Render "n/a", never the string "null" |
| Org with no `usage_decline` suggestions yet | Precision read-out shows 0/0/0 with a "no suggestions yet" affordance, plus the warm-up explanation |
| Non-admin/owner viewing the queue | Existing role gating unchanged — do not alter it |
| Mode select set to `active` while `sustain_days` invalid | Block save, surface the 422 |
