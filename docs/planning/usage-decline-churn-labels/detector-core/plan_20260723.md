## 2. Why this module exists (do not skip)

The shipped trend stack exposes **edges**, not levels: `recompute_usage_scores` appends to
`pending_trend_transitions` **only on a state change**
(`services/worker-service/src/tasks/usage_metrics.py:635-638`). A customer who enters
`sharp_decline` and stays there produces exactly **one** event — on day 1, the moment of *least*
evidence.

This module supplies the missing level-based concept: *has this decline been sustained?* — plus the
population-level outage guard (PRD M3b), which is what stops a broken usage pipeline from
presenting the operator's entire customer base as churned.

## 3. Implementation Phases

### Phase 1 — `qualifying_streak`

- **Goal:** Decide whether a customer's recent snapshots constitute a sustained decline, and return
  the streak's start date.
- **Files:**
  - `services/backend-api/tests/test_usage_decline_labels_core.py` (RED first)
  - `services/backend-api/src/services/usage_decline_labels_core.py`
- **Signature:**
  ```python
  def qualifying_streak(
      states: List[Tuple[date, str]],   # (snapshot_date, usage_trend_state), newest LAST
      sustain_days: int,
  ) -> Optional[date]:                  # streak start date, or None
  ```
- **Rules — each one gets its own test, written and watched failing first:**
  1. The most recent `sustain_days` snapshots are all `sharp_decline` → return the first date of
     that run.
  2. `sustain_days - 1` consecutive → `None`. **Test both sides of the boundary.**
  3. A `stable` anywhere in the window breaks the streak.
  4. **`insufficient_history` breaks the streak.** It is an absence of evidence, not evidence of
     stability. This is the subtlest rule in the aspect — pin it explicitly.
  5. `declining` never qualifies in v1 — not alone, not mixed with `sharp_decline`.
  6. **A calendar gap breaks the streak.** "Consecutive" means consecutive *dates*, not "the last N
     rows that happen to exist". A missing snapshot_date (worker outage) must not be silently
     bridged. This makes the detector conservative under our own downtime — the right direction.
- **Validation:** `./venv/bin/pytest tests/test_usage_decline_labels_core.py -v`
- **Commit:** `feat(usage-decline-churn-labels): sustained-decline streak core`

### Phase 2 — `suggestion_key`

- **Goal:** A deterministic natural key that makes re-detection idempotent while still allowing a
  genuine second decline episode.
- **Signature:** `def suggestion_key(email: str, streak_start: date) -> str`
- **Base form:** `f"usage:{email}:{streak_start.isoformat()}"`
- **THE CONSTRAINT THAT WILL BITE:** `ChurnLabelSuggestion.external_opportunity_id` is
  **`String(64)`** (`services/backend-api/src/models/churn_label_suggestion.py:48`), while
  `customer_email` is `String(255)`. The naive key overflows for long emails.
  - Required behaviour: when the natural key would exceed 64 chars, fall back to a **deterministic**
    hash form (e.g. `usage:{sha256(email)[:32]}:{iso_date}`) — still stable for the same
    (email, streak_start), because stability is what makes re-detection idempotent.
  - **Never truncate the email itself** — two customers sharing a long prefix would collide onto one
    suggestion, and the collision would be silent.
- **Tests (RED first):**
  1. Short email → readable natural form, ≤ 64 chars.
  2. **255-char email → still ≤ 64 chars** (the column max — the real boundary).
  3. Same (email, streak_start) called twice → identical output.
  4. Different streak_start → different key (a second episode can be suggested).
  5. Two distinct long emails sharing a 200-char prefix → **different** keys (no silent collision).
- **Commit:** `feat(usage-decline-churn-labels): stable suggestion key`

### Phase 3 — `build_evidence`

- **Goal:** The payload a human uses to judge a suggestion. This is the precision mechanism, not
  decoration — the operator is the only thing between a seasonal dip and a poisoned training set.
- **Returns** a JSON-serializable dict:
  `{trend_state, trend_pct, baseline_active_days_14d, current_active_days_14d, streak_days,
    streak_start_date, last_active_at, snapshot_series: [{date, active_days_14d}]}`
- **Tests (RED first):**
  1. Output survives `json.loads(json.dumps(out))` — **no `date`/`datetime` objects survive**;
     dates are ISO strings. (The column is `JSON`; a raw date raises at insert time, far from here.)
  2. `snapshot_series` preserves chronological order.
  3. `streak_days` matches the length implied by `streak_start_date`.
  4. `None` inputs (e.g. `trend_pct is None`) serialize as `null`, not the string `"None"`.
- **Note:** the key names here are a **contract** consumed by
  `../frontend-settings-and-evidence/` (`EvidenceCell`). Changing them later breaks the renderer.
- **Commit:** `feat(usage-decline-churn-labels): suggestion evidence payload`

### Phase 4 — `outage_suspected` (PRD M3b)

- **Goal:** Detect the instrumentation-outage signature *before* any suggestion is written.
- **Signature:**
  ```python
  def outage_suspected(qualifying: int, eligible: int, max_share: float, min_population: int) -> bool
  ```
- **Rules:**
  1. `eligible < min_population` → `False`. The ratio is meaningless in a tiny org (2 of 6 = 33%),
     and wrongly suppressing a small org's only signal is worse than the noise.
  2. Otherwise `True` iff `qualifying / eligible > max_share` — **strict `>`**, so exactly-at-
     threshold does **not** suppress.
  3. `eligible == 0` → `False`, never `ZeroDivisionError`.
- **Defaults:** module-level `DEFAULT_MAX_QUALIFYING_SHARE = 0.25`,
  `DEFAULT_MIN_POPULATION = 20`. Constants for v1 (neither value is validated); promote to config
  only if `worker-detector` finds a reason.
- **Tests (RED first):** each rule above, plus the exactly-at-threshold case and `eligible == 0`.
- **Commit:** `feat(usage-decline-churn-labels): population-level outage guard`

## 6. Edge Cases & Error Handling

| Case | Required behaviour |
|---|---|
| `states` shorter than `sustain_days` | `None` — never `IndexError` |
| `states` empty | `None` |
| `sustain_days <= 0` | Raise `ValueError`. The API layer already bounds this to [1,90]; a zero here means a caller bug and must be loud, not silently "everything qualifies" |
| Unsorted `states` input | Sort defensively by date inside the function, then evaluate |
| Duplicate dates in `states` | Treat as a data error — raise, don't guess |
| Email longer than the 64-char key budget | Deterministic hash fallback (Phase 2) |
| `eligible == 0` in `outage_suspected` | `False`, no division |
| Timezone-aware vs naive dates | `snapshot_date` is a `Date` column; compare dates only, never datetimes |

## 7. Agent Execution Notes

**Checkpoint for human review:** after Phase 2 — the hash-fallback key shape is the one decision
here with a lasting consequence (it lands in a unique constraint and cannot be changed later
without orphaning existing suggestions).

**Likely to need iteration:** the gap-detection rule in `qualifying_streak`. Getting "consecutive
calendar dates" right, including a gap at the *start* vs the *middle* of the window, is fiddlier
than it reads.

**Ask before proceeding if:** the streak semantics appear to conflict with how
`worker-detector` intends to query history (e.g. if fetching exactly `sustain_days` rows makes gap
detection impossible — in which case fetch `sustain_days` *calendar days* of rows instead, and say
so).

**Out of scope reminder:** do not touch `classify_usage_trend`,
`select_nearest_in_band_snapshot`, or `apply_trend_penalty` in `usage_score_service.py:203-366`.
