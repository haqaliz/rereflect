Source: `docs/planning/copilot-suggested-actions/prd.md` + `action-contract/spec.md`.
House commit style (`feat(...): ... (TDD)` / `test(...): RED — ...`).

tests that make disagreement fail loudly. It is deliberately first: both tests go RED here and
are turned GREEN by `deterministic-proposer` and `frontend-actions-ui` respectively.

## Phase 1 — The fixture

**Goal:** one committed JSON file that is the single definition of the `actions` item.

**Prerequisites:** none.

**Files:** `services/backend-api/tests/fixtures/copilot_actions_item.json`

**Steps:**

1. Write the fixture to exactly the envelope in the spec — a required `data_type`
   discriminator plus `data`, matching what `format_table`/`format_chart` already return
   (`response_formatter.py:58-61`, `:171-174`):

```json
{
  "data_type": "actions",
  "data": {
    "proposal_id": "msg-42:tag_customers:3f9a1c",
    "actions": [
      {
        "action": "tag_customers",
        "label": "Tag these 3 customers…",
        "params": {
          "emails": ["ada@example.com", "grace@example.com", "alan@example.com"]
        },
        "requires_input": ["tag"]
      }
    ]
  }
}
```

2. Use obviously-fake example.com addresses — the fixture is committed and read by two suites.
3. Keep exactly one action in the array. A second entry would let the frontend's
   one-button-per-action assertion pass by accident on a single-item loop bug.

**Validation:** `python3 -c "import json;json.load(open('services/backend-api/tests/fixtures/copilot_actions_item.json'))"`

**Commit:** `test(copilot-actions): golden fixture for the actions structured_data item`

## Phase 2 — Backend RED

**Goal:** a test asserting the backend emits exactly this shape. It must fail now, for the
right reason (no proposer exists), and go green in `deterministic-proposer`.

**Prerequisites:** Phase 1.

**Files:** `services/backend-api/tests/test_copilot_actions_contract.py`

**Steps:**

1. Copy the loader pattern from `test_intercom.py:583-600` — including its most important
   property, which must be preserved verbatim in spirit:

```python
GOLDEN_ACTIONS_PATH = (
    pathlib.Path(__file__).resolve().parent / "fixtures" / "copilot_actions_item.json"
)


def load_golden_actions_item() -> dict:
    """Load the actions-item contract shared with the frontend suite.

    Deliberately raises rather than skipping when the file is absent. A skip
    would turn the one test guarding this seam into a silent no-op -- which is
    the exact failure mode that let the Intercom envelope defect ship in every
    release, and which MessageBubble's silent data_type skip reproduces here.
    """
```

2. **Structural assertions** (these can pass now — they describe the fixture):
   - `data_type == "actions"`.
   - `data.proposal_id` is a non-empty string.
   - `data.actions` is a non-empty list; each entry has `action`, `label`, `params`,
     `requires_input`.
   - `requires_input` is a list of strings naming params the **user** supplies — assert
     `"tag" in requires_input` and assert `"tag" not in params`, pinning that the server never
     authors the tag value (PRD M6).
   - The item has no key outside `{data_type, data}` at the top level, except the
     chart-precedent allowance — assert the envelope explicitly so a future drift is caught.

3. **The RED assertion** — import the proposer and assert its output equals the fixture. Mark
   it clearly:

```python
@pytest.mark.xfail(
    reason="RED until deterministic-proposer lands; do not delete this marker "
           "without deleting the xfail",
    strict=True,
)
def test_proposer_emits_the_golden_actions_item():
    ...
```

   `strict=True` matters: once the proposer lands, an xpass **fails the suite**, forcing the
   marker's removal. A non-strict xfail would let the test rot silently.

4. Do **not** import `copilot_ws` at module scope in this file — keep the failure localised to
   the one test rather than collection-erroring the module.

**Validation:** `cd services/backend-api && pytest tests/test_copilot_actions_contract.py -v`
— structural tests pass, the proposer test is `xfailed` (not `error`, not `failed`).

**Commit:** `test(copilot-actions): RED — backend asserts the golden actions item (xfail strict)`

## Phase 3 — Frontend RED

**Goal:** a test asserting the renderer, given the same fixture, produces one button per
action — plus the negative test pinning the silent skip as deliberate.

**Prerequisites:** Phase 1.

**Files:** `services/frontend-web/__tests__/copilot/actionsContract.test.tsx`

**Steps:**

1. Read the fixture from the backend suite by relative path — the cross-service half of the
   golden-fixture pattern. Vitest runs in Node with jsdom, so `node:fs` is available:

```ts
import fs from 'node:fs';
import path from 'node:path';

// __tests__/copilot/ -> frontend-web/ -> services/
const FIXTURE = path.resolve(
  __dirname, '../../../backend-api/tests/fixtures/copilot_actions_item.json',
);
const goldenActionsItem = JSON.parse(fs.readFileSync(FIXTURE, 'utf-8'));
```

   Mirror the backend loader's posture: if the file is missing, **throw** — never skip.
   `fs.readFileSync` already throws, so simply do not wrap it in a try/catch.

2. Follow the existing `MessageBubble.test.tsx` setup for rendering a message with
   `structured_data`; that file is the closest template. There is no shared WS/test helper —
   the WebSocket mock is inline in `useCopilotWebSocket.test.ts` — but this aspect needs no WS
   at all: render `MessageBubble` directly with the fixture as the message's `structured_data`.

3. **The RED assertion:** rendering the fixture yields exactly one button whose accessible name
   is the fixture's `label`. This fails now because `MessageBubble.tsx:269-282` branches only on
   `'table'` and `'chart'`. Use `it.fails(...)` (Vitest's strict inverse assertion — it fails
   if the body passes) so it flips loudly when `frontend-actions-ui` lands.

4. **The negative test — the load-bearing one, and it passes now:**

```ts
it('renders nothing and does not throw for an unrecognised data_type', () => {
  // Pins MessageBubble's silent skip as DELIBERATE. If someone renames the
  // "actions" data_type, the fixture test above fails loudly instead of this
  // feature silently rendering nothing in production.
  ...
});
```

   Assert no button renders and no error is thrown.

5. Add a comment at the top of the file stating what the pair is for: backend asserts *"this is
   what I emit"*, frontend asserts *"given this, I render N buttons"*, and neither test alone
   would have caught the seam.

**Validation:** `cd services/frontend-web && pnpm vitest run __tests__/copilot/actionsContract.test.tsx`
— negative test passes, the render test reports as an expected failure.

## 5. Edge cases & error handling

- **Fixture missing/renamed** → both loaders throw. Deliberate; a skip would recreate the
  silent no-op this aspect exists to prevent.
- **Fixture edited on one side only** → that side's test fails. Intended; the fixture is the
  contract, and editing it is a deliberate contract change.
- **xfail becomes xpass** → `strict=True` fails the suite, forcing the marker's removal when
  the proposer lands. Same intent behind `it.fails` on the frontend.
- **Path traversal breaks** if either suite moves. Both paths are commented with the traversal,
  matching `test_intercom.py:584`.
- **Multi-tenancy:** not applicable — no route, no DB, no `organization_id` in this aspect. The
  fixture's emails are `example.com` placeholders, never real org data.

## 7. Spec ambiguities flagged

- `proposal_id` format is unspecified beyond "stable and deterministic". The fixture uses
  `msg-<id>:<action>:<hash>` illustratively; the real derivation is decided in
  `action-registry`/`deterministic-proposer`. The contract test asserts only that it is a
  non-empty string, so it does not over-constrain that decision.
- The spec allows a typed model for the actions item alone. This plan does **not** add one —
  everything on this path is raw dicts today, and a lone typed model buys nothing until there
  is a second producer.
