## 2. Decisions (settle here)

- **Where the action renders:** inside `MessageBubble` (the `structured_data` loop), **not** as a global Cmd+K surface (out of scope per spec). Unlike the `tableItem`/`chartItem` last-one-wins slots, actions accumulate into an array — the contract test renders one button per action and the fixture's `actions[]` can hold several.
- **Message reference for execution:** the persisted `conversation_id` + the `proposal_id` from the proposal itself. The frontend **never** uses the WS turn `message_id` — the execute route resolves the proposal by `conversation_id` + `proposal_id` (PRD OQ2). Thread `conversationId` as a new prop from `ChatArea` (which knows the active conversation).
- **Outcome display:** inline under the message (survives page revisit, preserves `errors[]` detail) **plus** a `toast` headline (house-standard, `RunPlaybookDropdown.tsx:53` pattern).
- **Role hiding:** show the action only for `user?.role === 'owner' || user?.role === 'admin'` (`useAuth()`; cosmetic — the server enforces).

## 6. Edge Cases & Error Handling

- Empty/whitespace tag → refused client-side, no network call (server would 422).
- Member role → action hidden (cosmetic); if reached, server 403 → clear message, no generic toast.
- Failure → error surfaced inline, button re-clickable, nothing marked executed.
- Success → executed state; the server-side one-shot guard is the real enforcement (button state is cosmetic).
- Re-adding an existing tag counts toward `updated` (set-union) — copy must not over-claim ("3 matched, 3 updated" only when true; show `errors[]` when present).
- `structured_data` is unsanitised end-to-end: render `label`, emails, and all item values as plain text.
