         """R1 — Intercom's per-query total_count rides the 3-tuple."""
         import httpx

         from src.clients.intercom import IntercomClient

         def handler(request: httpx.Request) -> httpx.Response:
             return httpx.Response(

## 8. Spec ambiguities flagged

1. **`total_count` "int" — no type guard.** Spec says "int when present, `None` when absent" but doesn't say what to do if Intercom ever sends a non-int (e.g. a string). This plan passes it through unvalidated (shape-transparent client, zero validation precedent); if sync-estimate's `max(0, total_count - conversations_seen)` ever hits a string, that aspect decides the guard. Flagged, not blocking.
2. **`_fake_client` call sites: 2-tuple or 3-tuple?** The spec says "the `_fake_client` fixtures update" but is silent on whether each call site must pass a `total_count`. This plan keeps call sites at 2-tuples and pads with `None` inside the fake — the fixture's OUTPUT (what sync tests observe) is what must match the real client, and it does. Concrete totals enter via sync-estimate's tests.
3. **Explicit-`null` vs absent `total_count`.** Both land as `None` via `payload.get` — one test covers the absent case, which is the same code path as `null`. No separate test needed; noted for the record.
4. **Consumer sites beyond the test file.** The dig (spec.md:39-41) enumerated the three; the repo-wide grep this plan ran adds two sites worth recording as "no change": `intercom_sync.py:303` (`if not sources` — read-only use of loop variables, no unpack) and `_fake_client_with_parts` (composition, not unpack). Both verified no-op.
