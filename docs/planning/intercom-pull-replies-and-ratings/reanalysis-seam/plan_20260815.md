## Task 0 — Verified seam (recorded, no code)

**How the UI "Re-analyze" action re-analyzes — traced end to end on 2026-08-15:**

| Step | File:line | What happens |
|---|---|---|
| UI action | `services/frontend-web/app/(dashboard)/feedbacks/[id]/page.tsx:238-248` | Actions dropdown → `handleAnalyze` → `await feedbackAPI.analyze([feedback.id], true)` at :242 (menu label :488) |
| API client | `services/frontend-web/lib/api/feedback.ts:183-189` | `analyze(feedbackIds, force=false)` → `POST /api/v1/analyze/` `{feedback_ids, force}` |
| Backend route | `services/backend-api/src/api/routes/analyze.py:38-81` | with `force=true`: clears `sentiment_label` + `churn_risk_factors` per item, **commits** (:64-69), then `send_task("src.tasks.analysis.analyze_feedback_batch", args=[org_id, ids])` (:73-76) |
| Worker task | `services/worker-service/src/tasks/analysis.py:225-277` | `analyze_feedback_batch(org_id, ids)`: filter `sentiment_label == None` (:244), per-item `_analyze_feedback_item` in its own try/except (:253-259), commit (:261), cache invalidation (:263-265), auto-assign (:267-270) |
| Core pipeline | `analysis.py:399-511` | LLM-first / keyword-fallback, classifier overrides, churn factors; with `customer_email` + db: `request_health_recompute` (:488-489), `update_churn_probability` (:494-495), `check_winback` (:504-505) |

**Does a force seam exist?** YES — the UI force path exists, but it is **split across the API boundary**:

- `analyze_single_feedback` (:145-217) has **no force flag** — the skip gate at :166-168 returns `already_analyzed` for any item with `sentiment_label` set.
- Force semantics live in the **backend route** (sentinel clearing, analyze.py:64-69) + the batch task honoring the cleared sentinel (`analyze_feedback_batch` itself has no force param — it filters on the cleared `sentiment_label`, :244).
- **There is no worker-side callable that force-re-analyzes**, and worker-service cannot import backend-api routes (CLAUDE.md: the worker image copies only `worker-service/src` + `analysis-engine/src/analyzer`).

**Decision (spec OQ1 / PRD OQ1 resolution):** reuse the existing force path — **do not** add a force flag to `analyze_single_feedback`, **do not** build a parallel pipeline. Ship one thin worker-side entry point that replicates the route's two steps (same sentinel fields, same task, same args), so a manual re-analyze and the pull's re-analysis are identical **by construction**: both end in `analyze_feedback_batch` → `_analyze_feedback_item`.

## Phase 2 — GREEN: the pull-facing seam

**File:** `services/worker-service/src/tasks/analysis.py` — add one function next to `analyze_feedback_batch` (before `_analyze_feedback_item`):

```python
def reanalyze_feedback(db, feedback_id: int) -> bool:
    """Force re-analysis of one feedback item — the pull-facing half of the
    UI "Re-analyze" seam (POST /api/v1/analyze, force=true; see
    backend-api/src/api/routes/analyze.py:64-76, which worker-service cannot
    import). Exactly mirrors that route: clear the two sentinel fields
    analyze_feedback_batch filters on, COMMIT so the queued task's new
    session sees them, then dispatch the same batch task with the same args.

    Must NOT use analyze_single_feedback: its skip gate (sentiment_label set
    -> already_analyzed) makes it a silent no-op for analyzed items. Returns
    False (no dispatch) when the item does not exist.
    """
    from src.models import FeedbackItem

    feedback = db.query(FeedbackItem).filter(FeedbackItem.id == feedback_id).first()
    if not feedback:
        return False
    feedback.sentiment_label = None
    feedback.churn_risk_factors = None
    db.commit()
    analyze_feedback_batch.delay(feedback.organization_id, [feedback_id])
    return True
```

**Design notes (do not deviate):**

- **Sentinel parity:** exactly the two fields analyze.py:67-68 clears. `churn_risk_factors` is cosmetic for the batch filter (only `sentiment_label` gates it, :244) but is cleared for parity with the manual path.
- **Commit-before-dispatch is mandatory:** the batch task runs in a fresh session and filters on the cleared sentinel; an uncommitted clear silently skips the item (test 3). The helper commits mid-`_sync_org`-transaction — safe because ingestion/enrichment are idempotent and a lost dispatch self-heals via the 30s `process_unanalyzed_feedback` beat (analysis.py:310-377).
- **Task choice:** `analyze_feedback_batch`, never `analyze_single_feedback` (the OQ1 trap). One dispatch per changed id = bounded fan-out (PRD S1 intent).
- **In-process `.delay()`** is the established worker pattern (`source_events.py:389-390`).
- **Documented equivalence:** like the manual path, the batch task does NOT fire webhook dispatch or feedback-automation triggers (only `analyze_single_feedback` does, :183-206) — identical by construction; do not "improve" it here.
- No other line in `analysis.py` changes. `analyze_single_feedback`'s signature, skip gate, and `analyze_feedback_batch`'s behavior stay untouched.

## Edge cases

| Case | Expected |
|---|---|
| Item not found | `False`, no dispatch, no raise (test 2) |
| Already-analyzed item, no force | `analyze_single_feedback` still returns `already_analyzed` — default behavior byte-identical (test 5) |
| `customer_email` present | Health recompute + churn probability + winback fire with `(org_id, email)` — same as fresh analysis (test 7) |
| Analysis failure for one item | Caught per-item in the batch loop → `failed` count, no raise; sync loop unaffected because dispatch is async (test 8) |
| Broker down at dispatch | `.delay` raises inside the sync task → task retry. Loud, never swallowed (matches `source_events.py:389-390`) |
| Mid-sync commit of sentinel clear | Safe: idempotent enrichment; lost dispatch self-heals via `process_unanalyzed_feedback` beat |
| Item created AND enriched in the same run | Create path already dispatched `analyze_single_feedback`; seam adds a batch dispatch → possible double-analysis, benign (skip gate or same-pipeline overwrite). Flag for `pull-enrichment`, not handled here |
| Redelivery / re-run of unchanged conversation | No new parts → not changed → seam never called (enrichment-level guard, `pull-enrichment` AC2) |
| Multiple changed items | One dispatch per changed id (bounded fan-out, PRD S1) |
| `churn_risk_factors` parity | Cleared even though the batch filter only gates on `sentiment_label` — cosmetic parity with analyze.py:67-68 |

## Ambiguities flagged

1. **PRD S1 wording vs the real path.** S1 says "one `analyze_single_feedback.delay` per changed item" — that task skips already-analyzed items (analysis.py:166-168) and would be a silent no-op. The UI actually force-re-analyzes via `analyze_feedback_batch` (sentinel clear + batch task). This plan reuses the **real** path; S1's intent (bounded fan-out, not per-part loop) is met.
2. **Mid-sync commit.** `reanalyze_feedback` commits inside `_sync_org`'s caller-managed transaction (mirrors analyze.py:69). The only alternative (two-phase clear/collect + post-commit dispatch) was rejected: it splits the seam into two callables and is not what the route does. Safety argument documented above.
3. **No webhook/automation dispatch on re-analysis.** The batch task (and therefore manual re-analyze AND the pull) does not fire webhook/automation triggers — only `analyze_single_feedback` does. Identical by construction; flagged, not changed.
4. **"Unchanged never dispatches" guard split.** The seam-boundary half (empty changed set → zero dispatches) lives here (test 9); the redelivery-level guard needs the enrichment helper and ships with `pull-enrichment` (its spec AC2).
