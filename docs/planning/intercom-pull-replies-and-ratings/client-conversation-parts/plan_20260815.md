     ```python
     def get_conversation(self, conversation_id: str) -> Dict[str, Any]:
         """Fetch one conversation's full detail payload.

         Returns the raw response object: `conversation_parts.conversation_parts[]`
         holds the reply parts and `rating` the satisfaction rating, parsed by the
         adapter, not here. 404 -> IntercomNotFoundError (caller: idempotent noop);
         401/403 -> IntercomAuthError; 429/5xx/network -> IntercomTransientError.
         """
         try:
             resp = self._client.get(
                 f"{INTERCOM_API_BASE}/conversations/{conversation_id}",
                 headers={
                     "Authorization": f"Bearer {self._access_token}",
                     "Accept": "application/json",
                     "Content-Type": "application/json",
                 },
             )
         except httpx.HTTPError as exc:
             raise IntercomTransientError(str(exc)) from exc

         return self._handle(resp).json()
     ```

## 6. Edge Cases & Error Handling

| Case | Handling (pinned) |
|---|---|
| `display_as` omitted (default) | Body key omitted entirely — existing `search_conversations` contract preserved byte-for-byte (AC3; test 2). All existing positional callers (intercom_sync.py:147) unaffected since the param is appended last. |
| Item without `conversation_parts` / `rating` (conversation has no replies, or not yet rated) | Client leaves the dict untouched — no synthesized empty objects (test 4). The adapter aspect handles absence. |
| `_normalize` interplay | `_normalize` (clients/intercom.py:241-253) only adds `conversation_message` from `source`; `conversation_parts`/`rating` ride through `dict(conversation)` untouched. No change to `_normalize`. |
| 401/403 | `IntercomAuthError` via shared `_handle` — operator-recoverable, no auto-disable, no retry (D7). |
| 429 | `IntercomTransientError` with `Retry-After` in the message — task-level retry (`task_self.retry`, max 3, delay 60) is the pull task's existing behavior; nothing new needed. |
| 404 | `IntercomNotFoundError` (already landed by the write-client aspect) — R1b's key case: conversation deleted between search and detail = caller noop, never an auth error. |
| ≥500 / network failure | `IntercomTransientError` — retryable. |
| Other 4xx (400/422/405…) | `IntercomAuthError` via the existing fallback — unchanged. |
| Heavier search payload with parts | `display_as` responses are larger; the client does nothing special — the pull-enrichment aspect's R5 bound (20-page cap, cursor resumes) is the guard; per_page default stays 100. |
| R1b per-run cap / drop count | Out of scope by spec — pull-enrichment aspect owns it (prd.md R5 "mirror the usage-decline per-run cap pattern"). The client only raises the taxonomy. |
| Timeout | Client-wide `_TIMEOUT_SECONDS = 30.0`; no per-call override (spec: follow the existing client defaults). |
| Token never logged | Guaranteed by existing `__repr__`; new methods use only the injected `self._access_token` for the header. |

## 8. Spec ambiguities flagged

1. **`display_as` placement (body field vs query param)** — the spec's OQ (spec.md:50). Assumed body field per Intercom's documented search schema; Phase 0 fact 1 verifies, smoke check confirms. If it's a query param, R1a changes to `params={"display_as": "conversation_parts"}` on the POST — a 3-line diff, but it must be decided in Phase 0, not in the adapter phase.
2. **Rating location on the conversation object** — assumed top-level `rating` object (`{type: "conversation_rating", rating, remark?, created_at?}`). The alternative (a part with `part_type: "customer_satisfaction_rating"`) changes the adapter's `extract_rating` input, not this client (raw passthrough) — flagged for the smoke check (Phase 2 item 4) and prd.md OQ3 (`rated_at` availability).
3. **Whether the parts array includes the first message** — assumed NOT in the parts array (it lives in `source`); if the real API duplicates it as a part, the adapter's "exclude the first message" rule must filter by part identity/`part_type`. Flagged as smoke-check item 3; the fixture keeps them separate.
4. **Search-with-parts response == detail response shape** — assumed identical for the parts/rating keys (`conversation_parts.conversation_parts[]` is the exact path `adapter.fetch_context` already parses, adapters/intercom.py:221). If search-with-parts nests differently (e.g. `data[]` wrapper), R1a's test 3 pins the divergence and the fallback (R1b) is the answer.
5. **`part_type` values for the reply family** — the fixture uses `"comment"`; the authoritative list ("comment"-family vs `conversation_created`/`note`/`assignment`/`close`…) is the **adapter aspect's** extraction contract — this plan deliberately leaves the client shape-agnostic and records the boundary.
6. **R1b payload weight / rate limits** — search-with-parts responses are heavier and the Intercom search API has its own rate-limit profile; the client cannot bound fan-out, so R5's per-run cap lives entirely in pull-enrichment. Flagged so the adapter/pull phases don't assume the client bounds anything.
7. **Task-0 record location** — the spec's AC1 only requires the verification be *recorded*; this plan lets the implementer pick spec.md vs this plan as the single record. Pick one; the adapter phase must be able to cite it.
