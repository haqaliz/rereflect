## 1. Placement decisions (pinned)

### 1.1 The enrichment pass lives in a module-level helper, not inline in `_sync_org`

```python
# in services/worker-service/src/tasks/intercom_sync.py
def _enrich_conversation_replies(db, item, reply_parts, rating) -> bool:
    """Merge NEW reply parts into item.text and item.source_metadata.

    Diff is by part_id membership against source_metadata["replies"].
    Returns True iff item.text actually changed (new replies merged);
    a rating-only update returns False (metadata changed, no re-analysis).

    Never touches customer_email (admin/bot rule — adapter contract).
    """
```

- Keeps `_sync_org` (:111-214) readable; the seam test targets the helper directly.
- It is task glue, not a pure service — it lives in `intercom_sync.py` beside the task
  (matches how other per-task helpers live in their task module), not in `src/services/`.
- `reply_parts` is the adapter aspect's `extract_reply_parts(conversation)` output
  (`[{part_id, author, body, created_at}]`, HTML-stripped, first message excluded).
- `rating` is the adapter aspect's `extract_rating(conversation)` output
  (`{rating, remark?, rated_at?}`) or `None`.
- The merge block format is the adapter contract, used verbatim:
  `"\n\n--- Reply by {author_name} ({created_at}) ---\n{body}"`.

### 1.2 Wiring point inside `_sync_org`

After the `for source in sources:` loop, still inside `for conversation in conversations:`
(`intercom_sync.py:153-181`), and after the `if not sources: continue` guard (:160-161):

```text
1. Extract parts + rating from the conversation (see §2 gate: R1a reads them off the
   search object; R1b fetches via client.get_conversation with the per-run cap).
2. If not parts and not rating → continue (no DB lookup for unchanged conversations).
3. Load the item: db.query(FeedbackItem).filter(
       FeedbackItem.organization_id == org_id,
       FeedbackItem.source == "intercom",
       FeedbackItem.source_external_id == conversation_id).first()
   — the existing ix_feedback_items_org_source_external index
   (backend-api/src/models/feedback.py:85) serves this exact shape.
4. If item is None → continue (no item → nothing to enrich).
5. changed = _enrich_conversation_replies(db, item, parts, rating)
6. If changed → changed_feedback_ids.append(item.id)
```

- One code path for created and pre-existing items: for a just-created item the lookup
  autoflushes and finds it (creation already `db.flush()`ed it, source_events.py:375).
- The same `>=` boundary conversation re-fetched across runs hits step 2/3 again; the
  part_id diff (helper step 3) makes the second visit a no-op — that is the idempotency.

### 1.3 Re-analysis dispatch happens AFTER commit — pinned

`_sync_intercom_org_body` owns the transaction (`intercom_sync.py:223-278`). `_sync_org`
returns `changed_feedback_ids` in its result dict; the body:

```text
db.commit()                                      # :265 — text/metadata persisted
reanalyze_feedback_ids(org_id, result["changed_feedback_ids"])   # reanalysis-seam seam
cache_invalidate(...)                            # :267-270 — unchanged
```

The item's new text/metadata must be committed before the re-analysis task reads it —
dispatch after `db.commit()`, never before, never inside `_sync_org`. The seam call is
guarded so it can never break the sync (its own task does the retrying).

### 1.4 Counter semantics — pinned

`conversations_ingested` counts **items created** this run (`feedback_created`, :180-181).
Enrichment **never touches it**: a run that only merges replies into an existing item
reports `conversations_ingested == 0` but still dispatches re-analysis. No existing
counter changes; `_sync_org`'s result dict gains `changed_feedback_ids` (and
`dropped_by_cap` under R1b) — additive, nothing removed.

### 1.5 Rating semantics — pinned

- Rating/remark/rated_at are stored in `source_metadata` only (`rating`, `remark`,
  `rated_at` when present). **Never in `text`.**
- Rating-only change (new rating, no new replies) → metadata updated, **no dispatch**:
  re-analysis inputs (text, customer_email) did not change, so an LLM pass would be pure
  churn. "Content changed" (spec step 4, PRD R4) = text changed = ≥1 new reply merged.

### 1.6 Admin/bot authors — pinned

Enrichment writes **only** `item.text` and `item.source_metadata`. `customer_email` is
never assigned by the helper (the first-message author's email was set at creation,
source_events.py:372). A reply from an admin/bot is merged as content; its author's
email can never reach `customer_email`. Test asserts the field is untouched.

### Phase 1 — `_enrich_conversation_replies` helper (seam unit tests)

- **Goal:** the merge/diff/metadata logic exists and is pinned by direct unit tests.
- **Files:** `services/worker-service/tests/test_intercom_enrichment.py` (new, RED);
  `services/worker-service/src/tasks/intercom_sync.py` (helper).
- **RED first:**
  1. **Happy path:** item with `text="First message"`, one new reply part →
     `text` ends with `"\n\n--- Reply by Dana Okafor (2026-08-01T10:00:00Z) ---\nI fixed it"`,
     `source_metadata["replies"]` contains the part (full part object), returns `True`.
  2. **Multiple replies, in order:** two new parts → both blocks appended in given order.
  3. **Idempotent re-merge:** call again with the same parts → text unchanged (exact
     equality), metadata unchanged, returns `False`. **The single most important test.**
  4. **Mixed known/new:** part A known, part B new → only B's block appended.
  5. **Rating stored, not in text:** rating passed → `source_metadata["rating"]` /
     `["remark"]` / `["rated_at"]` set, `text` does NOT contain the rating, returns
     `False` when no new replies (metadata-only change).
  6. **Rating absent → untouched:** existing rating in metadata survives a no-rating call.
  7. **`source_metadata` None → starts fresh** (item created before this feature).
  8. **customer_email never written:** helper called with an admin-authored part
     (`author["type"] == "admin"`) → `item.customer_email` unchanged (assert the exact
     prior value).
- **Edge pins in the same phase:** empty `reply_parts` list → `False`, no mutation;
  duplicate `part_id` within one payload → merged once.
- **Commit:** `test(worker): RED — intercom reply enrichment merge helper`
- **Commit:** `feat(worker): intercom reply+rating enrichment merge helper (TDD)`

- New fake-client helper `_fake_client_with_parts(pages, ...)` alongside `_fake_client`
  (:129-145) — same normalization discipline (pass through `IntercomClient._normalize`).
- **RED first (via `_sync_org`, same style as `TestSyncOrg`):**
  1. **Enrichment happy path (AC1):** one conversation, two replies + rating → exactly
     ONE `FeedbackItem`; `text` = first message + two merge blocks; `source_metadata`
     has `replies` (2 parts) + `rating`/`remark`; `result["conversations_ingested"] == 1`
     (created this run); `result["changed_feedback_ids"] == [item.id]`.
  2. **Redelivery idempotency (AC2):** `_sync_org` twice, same conversation+parts →
     second run `conversations_ingested == 0` (dedup), `text` byte-identical, metadata
     unchanged. (The `>=` boundary re-fetch is exactly this shape.)
  3. **No-change → nothing dispatched:** as the seam is called post-commit by the body
     (§1.3), assert at the `_sync_org` level that `changed_feedback_ids == []` on the
     second run; the dispatch-zero assertion itself is Phase 3.
  4. **Admin/bot reply merged, not attributed:** conversation with a customer first
     message + admin reply → text includes the admin's body; `item.customer_email` is the
     first-message author's email, never the admin's.
  5. **Counter semantics (AC "counter unchanged"):** pre-existing item (created by a
     first run without parts) + second run with one new reply →
     `conversations_ingested == 0`, `changed_feedback_ids == [item.id]` — enrichment
     dispatches without inflating the counter.
  6. **Conversation without parts:** no crash, no dispatch, no lookup side-effects
     (`changed_feedback_ids == []`).
  7. **Conversation with parts but no item** (no source match): no crash, no dispatch.
  8. **Rating-only change:** second run where only the rating differs → metadata updated,
     `changed_feedback_ids == []`.
  9. **Org scoping:** same conversation id under a second org with its own item →
     enrichment touches only that org's item (cross-tenant guard on the lookup).

### Phase 3 — post-commit re-analysis dispatch

- **Goal:** changed items are re-analyzed exactly like a manual UI re-analyze; unchanged
  items are never dispatched (R4 + S1: one dispatch per changed item, bounded fan-out).
- **Files:** `services/worker-service/src/tasks/intercom_sync.py`
  (`_sync_intercom_org_body`); tests in `test_intercom_enrichment.py` or a small
  `TestSyncOrgDispatch` class.
- **RED first** (through `_sync_intercom_org_body` with `_patch_db_session`,
  monkeypatched reanalysis seam — mirror `TestAuthFailureHandling`'s shape):
  1. **Changed → dispatched once:** org with one enriched item → seam called with
     `(org_id, [item.id])`, exactly once.
  2. **Unchanged → never dispatched:** second run (or an unchanged conversation) → seam
     not called (the "silently never fires" guard family).
  3. **Ordering pin:** the seam is called only after `db.commit()` — assert via a
     side_effect that records commit state, or assert the sync transaction committed
     (item reload sees the new text) before the seam received the id. This is the
     `in-side_effect` assertion technique the worker-detector plan used (Phase 5).
  4. **No items / no sources:** seam never called, task still returns `{"status": "ok", …}`.
- **Commit:** `feat(worker): dispatch re-analysis for enriched intercom items post-commit (TDD)`

## 7. Edge Cases & Error Handling

| Case | Required behaviour |
|---|---|
| Conversation without parts (R1a) / detail fetch fails → no parts (R1b) | No-op: skip lookup, no dispatch |
| Conversation seen again (boundary `>=` re-fetch, redelivery, next run) | part_id diff → no text change, no metadata change, no dispatch |
| Rating present | Stored in `source_metadata` only; never in `text`; rating-only change → no dispatch |
| Rating absent but previously stored | Existing `rating`/`remark`/`rated_at` preserved |
| Admin/bot-authored reply | Content merged; `customer_email` never written (asserted) |
| Item already deleted / no item | Skip silently (nothing to enrich) |
| Same conversation id in another org | Lookup is org-scoped (`organization_id`, `source`, `source_external_id`); cross-tenant isolation asserted |
| `source_metadata` is NULL (pre-feature items) | Treated as empty dict; first enrichment writes `replies` |
| R1b cap exceeded | `dropped_by_cap` counted + WARNING logged once; run continues; cursor resumes next run |
| R1b `get_conversation` 429/5xx | `IntercomTransientError` → task retry (existing body handler); cursor not advanced (no commit) |
| 401/403 on parts fetch | `IntercomAuthError` → D7: status recorded, no retry, org stays active (existing body handler) |
| Enrichment raises mid-run (unexpected) | Bubbles like any sync failure → whole org run retried; same failure semantics as the event loop (D2 in-process design) |
| Perf | ≤1 indexed SELECT per conversation with parts (≤3000/run worst case), 0 client calls under R1a; acceptable for a 15-min tick |
