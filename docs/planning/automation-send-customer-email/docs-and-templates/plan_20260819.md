## 1. Verified ground truth (read from the tree) — and spec discrepancies

Every claim below was read from the worktree before writing this plan. This is the contract the implementation must match.

### 1.1 Template dict shape — `services/backend-api/src/config/automation_templates.py`

- Keys per entry: `id`, `name`, `description`, `trigger: {type, config}`, `actions: [{type, config}]`, `cooldown_hours`, and an **optional** `mode` key (`"shadow"` for templates 6/7; defaults to `"active"` when absent, honored by `enable_template` at `src/api/routes/automations.py:579` via `tmpl.get("mode", "active")`). Module header comment (lines 1-16) documents the `mode` convention — it must be updated to mention template 8.
- `TEMPLATES_BY_ID` (line 215) is derived — no manual edit needed.
- **No existing template uses `churn_probability_threshold`** — there is no prior template convention to copy; the trigger's semantics must come from the engine (below).

### 1.2 `churn_probability_threshold` trigger config — the spec's `{threshold, direction}` guess

- Engine evaluation, `_trigger_churn_probability` (`src/services/automation_engine.py:353-358`): reads **only** `cfg.get("threshold", 0.7)` and fires when `context["churn_probability"] >= threshold`. There is no `direction` read and no "below" path — the trigger is structurally level-based and always "≥".
- Activation seeding, `seed_churn_cooldowns` (`src/services/automation_engine.py:826-876`): reads **only** `(rule.trigger_config or {}).get("threshold", 0.7)` (`:852`) to find currently-above-threshold customers.
- API validation, `ChurnProbabilityConfig` (`src/api/routes/automations.py:106-115`): **does** define `direction: str = "above"` with a validator that forces the value to `"above"` (110-115). So `{threshold: 0.6, direction: "above"}` is **schema-valid** — but `direction` is functionally inert in the engine and in `seed_churn_cooldowns`.

**Decision (discrepancy resolution):** ship the spec's form verbatim —
`"config": {"threshold": 0.6, "direction": "above"}` — for round-trip fidelity with a user-created rule (the frontend/API always carries `direction: "above"`), and add a one-line code comment noting `direction` is accepted-but-inert (evaluation is always `>= threshold`). `{threshold: 0.6}` alone would also work; the spec's form is preferred for rule-shape parity. The plan's test pins the exact config keys we ship, so this is locked at implementation time.

### 1.3 Seeding is static + `enable_template`, not a runtime seeder

There is no `automation_template_seeder.py`. "Idempotent at startup" (spec) actually means: `AUTOMATION_TEMPLATES` is a module-level static list, and `POST /api/v1/automations/templates/{id}/enable` (`src/api/routes/automations.py:546-593`) instantiates an `AutomationRule` directly from the dict (lines 575-589). `enable_template` does **not** run `TriggerSchema`/`ActionSchema` — so a bad template would create a rule the API would have 422'd or the engine would silently skip. The existing parametrized tests (`test_every_template_trigger_config_passes_trigger_schema` in both `test_automation_template_usage_trend.py:96-100` and `test_automation_template_batch_sentiment.py:76-80`) are the guard; this plan extends the same guard to `ActionSchema` for the new template.
