     b. **ok → sent** — sender returns `{"ok": True, "status": "sent", "reason": ""}` ⇒ row

     ```python
     @shared_task(bind=True, name="tasks.outreach.send_automation_email")
     def send_automation_email(self, delivery_id: int) -> dict:
         """Send one automation-customer email; never leaves the row queued.

         Task name is byte-identical to the backend engine's dispatch string
         (`action-core` enqueues via send_task("tasks.outreach.send_automation_email")).
         """
         with get_db_session() as db:
             try:
                 return _process_automation_delivery(db, delivery_id)
             except Exception as exc:
                 logger.exception(
                     "outreach task: unhandled exception delivery=%s: %s", delivery_id, exc
                 )
                 try:
                     from src.models import AutomationEmailDelivery
                     delivery = db.query(AutomationEmailDelivery).filter_by(id=delivery_id).first()
                     if delivery is not None and delivery.status not in TERMINAL_STATUSES:
                         delivery.status = "failed"
                         delivery.reason = f"task error: {exc}"
                         db.commit()
                 except Exception as inner_exc:
                     logger.error(
                         "outreach task: failed to mark delivery %s failed: %s",
                         delivery_id, inner_exc,
                     )
                 return {"status": "error", "error": str(exc)}

     def _process_automation_delivery(db, delivery_id: int) -> dict:
         delivery = get_delivery_row(db, delivery_id)
         if delivery is None:
             logger.warning("outreach task: delivery %s not found", delivery_id)
             return {"status": "error", "error": "delivery not found"}
         if delivery.status in TERMINAL_STATUSES:
             return {"status": "skipped", "error": f"already terminal ({delivery.status})"}
         from src.models import Organization
         org = db.query(Organization).filter_by(id=delivery.organization_id).first()
         product_name = (org.product_name_display if org and org.product_name_display else "Rereflect")
         result = outreach_sender.send_outreach_email(
             db,
             org_id=delivery.organization_id,
             customer_email=delivery.customer_email,
             subject=delivery.subject,
             body=delivery.body,
             product_name=product_name,
             template_key=delivery.template_key,
         )
         if result.get("ok"):
             set_delivery_outcome(db, delivery, "sent", None)
         elif result.get("status") == "skipped":
             set_delivery_outcome(db, delivery, "skipped", result.get("reason", "skipped"))
         else:
             set_delivery_outcome(db, delivery, "failed", result.get("reason", "send failed"))
         return {"status": delivery.status, "error": delivery.reason}
     ```
     Imports are worker-local and plain (`src.models`, `src.services.outreach_sender`,
     `src.services.automation_email_delivery`) — no bare `except` around imports
     (`test_worker_import_sweep.py`).

## 6. Edge Cases & Error Handling

- **Never leaves `queued`:** the task wraps the send in try/except → any exception marks
  the row `failed` with `task error: ...` (mirroring `tasks/outreach.py:41-64`). A row that
  is already terminal is a no-op — duplicate dispatch (retry racing a live task) never
  resets or re-sends.
- **No-key:** evaluator skips loudly at enqueue (`email not configured`) — never a false
  success (PRD M4). The sender's own no-key check (`outreach_sender.py:176-177`) is the
  second layer for the toggled-between-enqueue-and-send case.
- **Opt-out toggled after enqueue:** the sender checks `outreach_opt_out` at send time
  (`outreach_sender.py:167-168`) → row `skipped: opted out`. Honest.
- **Org-wide trigger (batch_sentiment_threshold):** the feedback mirror skips loudly by
  TRIGGER TYPE (`rule.trigger_type in ORG_WIDE_TRIGGER_TYPES`), because the context's
  `customer_email` is the pivot feedback's email, not an org-wide recipient (PRD M4,
  §8 #4).
- **Archived customer:** evaluator checks `CustomerHealth.is_archived` (missing health row
  ⇒ not archived, sends — PRD R2). The sender does NOT check archived (verified) — this
  lives in the evaluator.
- **cs_assignee without a health row / owner / owner user:** loud error, no enqueue
  (mirrors the backend's loud-error behavior, `action-core` AC6).
- **Unknown template key / bad recipient / missing config:** loud action errors, no
  delivery row, no `.delay`.
- **Unknown action types in churn/usage mirrors:** STILL silently skipped — the existing
  pins `test_non_run_playbook_actions_are_ignored` (churn `:273`, usage `:452`) must stay
  green unmodified. Making them loud is a separate delivery-integrity hardening (PRD R3).
- **`run_playbook` in the feedback mirror:** still a loud unsupported error
  (`test_automation_feedback_trigger.py:419`) — unchanged.
- **Broker down at `.delay()`:** the evaluator logs a warning and still records the action
  as `{status: "queued", delivery_id}` with `error: None`; the row stays `queued` (R8:
  honest "work accepted, outcome unknown"), a re-fire creates a fresh row.

## 8. Spec-vs-Code Discrepancies Found (flag to reviewer)

1. **PRD M3 column list omits `body` (and `product_name`).** The PRD's column list
   (`prd.md:104-107`) has `subject` but no `body`; the worker-mirrors spec
   (`spec.md:15`) says the task loads `subject, body, product_name`, and
   `send_outreach_email` requires `subject` + `body` (the sender's actual signature is
   `send_outreach_email(db, org_id, customer_email, subject, body, *, product_name,
   template_key)` — `outreach_sender.py:139-148`). Resolution: the delivery row MUST carry
   `body`; this plan pins it in the worker mirror (Phase 1) and the parity test fails if
   `action-core` lands without it. `product_name` is NOT pinned on the row — the task
   derives it from `Organization.product_name_display` at send time (mirroring
   `tasks/outreach.py:107-114`), so the row does not need a product_name column.
2. **PRD M3 says "BigInt PK, codebase convention"** (`prd.md:105`) — no backend model uses
   `BigInteger`; every model in the codebase uses `Integer` PKs. The worker mirror uses
   `Integer` to match worker-mirror style; the backend model (action-core) should also use
   the same type the rest of the codebase uses. Minor doc inaccuracy; not a blocker.
3. **Feedback-mirror `_execute_actions` "unsupported action" error wording differs from the
   backend.** The feedback mirror says `"Unsupported action type in worker mirror: ..."`
   (`:508`) vs the backend's `"Unknown action type: ..."` (`automation_engine.py:430`).
   `send_customer_email` is now supported in both, so this difference no longer matters for
   it — but keep the mirror wording for genuinely unknown types.
4. **Org-wide skip is by trigger type, not by context value.** The worker-mirrors spec
   (`spec.md:16`) says "skip loudly on no-key / no customer_email / is_archived" and omits
   the org-wide case; PRD M4 (`prd.md:116-118`) requires the skip. Code reality: the
   feedback mirror's context ALWAYS carries a `customer_email` (the pivot feedback's,
   possibly `""`) even for org-wide `batch_sentiment_threshold` (`analysis.py:197-198`), and
   `_evaluate_rule` nulls it out for the execution log (`:275`). The handler must check
   `rule.trigger_type in ORG_WIDE_TRIGGER_TYPES` and skip loudly — this plan does that
   (Phase 3, step 2).
5. **`render_outreach_template` only renders the body.** The registry mirror's render
   function substitutes `{{CUSTOMER_NAME}}`/`{{PRODUCT_NAME}}` in the BODY only
   (`outreach_templates_mirror.py:75-85`); the SUBJECT needs the same substitution done by
   the caller (`playbook_engine.py:476-480`). The handler must substitute the subject too —
   this plan does that (Phase 3, step 2, item 7).
6. **`automation_execution_id` is always `None` from the worker mirrors.** The delivery
   model has the nullable column, but the execution row is created AFTER actions run
   (`_evaluate_rule` calls `_execute_actions` before building the `AutomationExecution`),
   so the delivery row cannot reference it. The backend engine has the same limitation
   (`automation_engine.py:407-438`). PRD R5 documents the execution-log-vs-delivery
   coupling; the deliveries surface (S2, action-core) is how operators see the outcome.
