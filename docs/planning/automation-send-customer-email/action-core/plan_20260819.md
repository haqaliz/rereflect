## Spec-vs-code discrepancies found during verification (all grounded in the worktree)

- **D1 — PK type.** PRD M3 says "BigInt PK, codebase convention", but every model in
  `services/backend-api/src/models/` (incl. `automation_execution.py`, `outreach_campaign.py`)
  uses `Integer` PKs. **Plan uses Integer** (the real convention).
- **D2 — missing `body` column.** PRD M3's column list omits `body`, but the worker task
  takes only `delivery_id` and `outreach_sender.send_outreach_email` needs subject+body
  strings (`worker-service/src/services/outreach_sender.py:139-155`). The spec's handler
  "renders subject/body"; the row must store the rendered body or the worker cannot send.
  **Plan adds `body` Text.** Verify with the worker-mirrors aspect owner.
- **D3 — org-wide trigger never reaches the backend engine.** `batch_sentiment_threshold`
  is not in the backend engine's `_check_trigger` dispatch (`automation_engine.py:216-235`)
  and `health_score_service.py:549-566` only dispatches `health_score_threshold` /
  `churn_risk_level_change` (always carrying `customer_email`). Spec AC4 is therefore
  exercised by calling the handler directly with a customer_email-less context; the
  handler treats missing/empty/`__org__` the same (loud org-wide skip).
- **D4 — `enable_template` bypasses action validation.** The template-enable route
  (`automations.py:546-593`) persists `tmpl["actions"]` directly without `ActionSchema` /
  `_validate_run_playbook_actions`. A seeded template with a bad `send_customer_email`
  config would persist — the engine handler must validate the template key at execution
  time (it does; Phase C).
- **D5 — `RESEND_API_KEY` is import-time-captured.** `email_service.py:14` reads
  `os.getenv` once at import; the no-key test must patch the module attribute, not
  `os.environ`.
- **D6 — `render_outreach_template` returns body only.** `outreach_templates.py:79-91`
  substitutes only into `body`; the subject (`"Your weekly {{PRODUCT_NAME}} digest"` for
  `weekly_digest_entry`) needs its own inline `{{PRODUCT_NAME}}` substitution in the
  handler.
- **D7 — spec says `app.send_task(...)`; the real precedent is `get_celery_app().send_task(...)`.**
  `_execute_run_playbook` (`automation_engine.py:779-783`) and `playbooks.py::_dispatch_celery`
  (`playbooks.py:221-226`) both use `get_celery_app().send_task("tasks.<...>", args=[id])`.
  Plan uses that exact shape.

  action config models (205-241), dispatchers (248-305), `_validate_run_playbook_actions`
