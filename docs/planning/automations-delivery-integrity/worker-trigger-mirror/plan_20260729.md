## Phase 2 — GREEN: the mirror module

**File:** `services/worker-service/src/services/automation_feedback_trigger.py` (new)

**Public entry point:** `evaluate_feedback_triggers(db, org_id: int, context: dict) -> List[Dict]`

**Steps:**

1. Module docstring stating: why this exists, that it mirrors
   `backend-api/src/services/automation_engine.py`, that the worker cannot import
   backend-api, and that **any change to trigger semantics must be made in both places**
   (spec W8).
2. `_get_redis()` — Redis **DB 1**, returns `None` on failure so cooldowns degrade to
   "always fire" and never raise. Copy `automation_churn_trigger.py`'s behaviour exactly.
3. Cooldown key: `automation_cooldown:{rule_id}:{customer_email}`, TTL
   `cooldown_hours * 3600` (spec W5). Assert the literal key string in a test — a typo here
   silently decouples the two processes.
4. Rule selection: `AutomationRule.organization_id == org_id`,
   `trigger_type IN ("feedback_category_match","sentiment_pattern")`,
   `mode.in_(["shadow","active"])`. `off` rules are never fetched.
5. Triggers (port verbatim from the backend engine):
   - `feedback_category_match` — `categories` list, optional `is_urgent`.
   - `sentiment_pattern` — ≥ `count` feedbacks with `sentiment` from the **same customer**
     within `days`.
6. Mode gating: `shadow` → log `status="shadow"` with `actions_executed=[]` and execute
   **nothing**; `active` → execute actions.
7. Actions — implement all four (spec W3): `auto_assign`, `change_status`,
   `send_notification`, `draft_response`. **Unimplemented types (incl. `run_playbook`) must
   append `{"type": t, "result": None, "error": f"Unsupported action type in worker mirror: {t}"}`
   — never a silent skip.**
8. `send_notification` supports `dashboard`, `email`, `slack` (spec W4), same loudness
   contract as aspect 1: unknown channel → warning + error string. Wrap the worker's Slack
   sender in `try/except` because it **raises**.
9. Write `AutomationExecution` rows in the same shape as `_log_execution`, with the same
   `success` / `partial_failure` / `failed` / `shadow` status computation.

**Validation:** `cd services/worker-service && ./venv/bin/pytest tests/test_automation_feedback_trigger.py -v`

**Commit:** `feat(worker): mirror feedback_category_match + sentiment_pattern triggers`

## Phase 4 — GREEN: shadow-on-repair migration

**File:** `services/backend-api/alembic/versions/<generated>_shadow_repaired_automation_triggers.py`

- `down_revision = "b2262e51eeb5"` (confirm with a live `alembic heads` first).
- Upgrade:
  ```sql
  UPDATE automation_rules
     SET mode = 'shadow'
   WHERE mode = 'active'
     AND trigger_type IN ('feedback_category_match', 'sentiment_pattern');
  ```
- Downgrade: **no-op with a comment.** Reversing it would re-activate rules an operator may
  have deliberately left in shadow — silently re-arming automations is worse than an
  irreversible data migration. State that reasoning in the docstring.
- Must not touch template defaults: rules created *after* this migration start `active` as
  normal.

**Tests** (`services/backend-api/tests/`): active `feedback_category_match` → `shadow`;
active `health_score_threshold` → unchanged `active`; already-`off` → unchanged `off`.

**Validation:** `./venv/bin/alembic upgrade head`, then `./venv/bin/alembic heads` prints
exactly one head.

## Edge cases

| Case | Expected |
|---|---|
| Redis unavailable | Cooldowns disabled, rules still evaluate. Never raises. |
| `customer_email` empty | Cooldown key degrades gracefully; matches backend behaviour. |
| Rule with an action type the mirror lacks | Explicit `error` in `actions_executed`, row is `partial_failure`. |
| Feedback with no matching rule | No `AutomationExecution` row. |
| Org has rules but all `off` | Not fetched; no rows. |
