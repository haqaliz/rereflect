### Phase 2 — `_handle_tag`

**Goal:** `tag` writes/dedupes/sorts the customer's tags with the bulk-tag constraints.

**Files:**
- `src/services/playbook_engine.py` (modify — new handler + `_dispatch_action` branch)
- `tests/test_playbook_tag_action.py` (create)

**Steps:**
1. Read the constraint source: `services/backend-api/src/api/routes/customers.py:655-681,713-724`
   (`_TAG_MAX_LENGTH=50`, `_TAG_CAP_PER_CUSTOMER=20`, trim/dedupe/sort, over-cap → row
   unchanged + error). Replicate those semantics in the worker handler.
2. **RED** — `tests/test_playbook_tag_action.py` (own builder helpers copied from
   `test_playbook_engine.py` fixture pattern; call `playbook_engine.execute(exe.id, db)`
   with a playbook whose `action_sequence` is `[{"type": "tag", "config": {"tag": "at-risk"}}]`):
   - AC1: tag added, sorted, deduped; persisted after the run
   - AC2: 21-tag row → `ok: False`, reason mentions cap, row unchanged; >50-char tag →
     `ok: False`; empty/whitespace tag → `ok: False`
   - AC3: `health.tags = None` → array initialized
   - AC8: `[{"type": "tag", "config": {"tag": "..."}}, {"type": "change_status", ...}]` —
     the failing tag does not stop `change_status`
3. **GREEN** — implement `_handle_tag(config, customer_email, health, db)`:
   - validate `config["tag"]`: str, trimmed, non-empty, ≤50 chars → else
     `{"ok": False, "result": None, "error": "<reason>"}`
   - `existing = health.tags or []`; `if config["tag"] in existing → {"ok": True,
     "result": {"tag": tag, "tags": existing}}` (idempotent no-op, honest result)
   - `if len(existing) >= 20 → {"ok": False, "error": "tag cap (20) reached"}`
   - `health.tags = sorted(existing + [tag])`; return
     `{"ok": True, "result": {"tag": tag, "tags": health.tags}}`
   - wrap persistence in `try/except` → rollback + `ok: False` on DB errors
   - add the branch in `_dispatch_action` after `_handle_send_email`
4. **REFACTOR** — nothing to extract yet; keep the handler self-contained.

**Validation:** `pytest tests/test_playbook_tag_action.py tests/test_playbook_engine.py -q`
**Commit:** `feat(tag-notify-actions): tag playbook action (worker engine, TDD)`

### Phase 3 — `_handle_notify`

**Goal:** `notify` delivers to Slack/Discord/dashboard per the org's connected integrations.

**Files:**
- `src/services/playbook_engine.py` (modify)
- `tests/test_playbook_notify_action.py` (create)

**Steps:**
1. Read the send seams first (worker): `src/notification_dispatch.py:578-672`
   (`dispatch_alert`), `:675-829` (slack/discord paths), `src/tasks/alerts.py`
   (`send_slack_message_webhook` :226, `send_slack_message_oauth` :261,
   `send_discord_message_webhook` :239 — **these raise**), and the channel-aware
   `send_notification` precedent in `src/services/automation_feedback_trigger.py:676-827`
   (how it selects the Slack integration, which channel field it reads, per-org once).
   Follow that precedent exactly for integration selection.
2. **RED** — `tests/test_playbook_notify_action.py` (own fixtures; monkeypatch the
   `tasks.alerts` senders and `notification_dispatch` calls with recording fakes):
   - AC4: `channel: slack` with an active Slack integration → sender called once per
     integration, result records the channel; raising sender → `ok: False` (run completes)
   - AC5: `channel: discord` with an active Discord integration → Discord sender called
   - AC6: `channel: dashboard` → `Notification` rows created for admins (preferences
     honored), result `{notifications_created: N}`
   - AC7: `channel: slack` with no connected Slack integration → `ok: False`, reason
     contains "no slack"; unknown channel → `ok: False`, reason contains "unknown channel"
   - AC8: failing `notify` doesn't stop sibling actions
3. **GREEN** — implement `_handle_notify(config, customer_email, health, db)`:
   - validate `message` (non-empty str); `channel = config.get("channel")`; normalize
   - `slack` → load active `Integration.type == "slack"` rows for the org (worker model
     `Integration` exists); none → `ok: False, "no slack integration connected"`; else
     for each, call the webhook/OAuth sender (same selection the feedback-trigger
     precedent uses) in `try/except` (senders raise) → aggregate
     `{"ok": True, "result": {"channel": "slack", "integrations_sent": N,
     "target": config.get("target")}}`
   - `discord` → same shape via the Discord sender
   - `dashboard` → reuse the `dispatch_alert`/notification-creation seam for admins
     (honor prefs); `{"ok": True, "result": {"notifications_created": N}}`
   - unknown channel → `{"ok": False, "error": f"unknown notify channel: '{channel}'"}`
   - any raise → `ok: False` with the exception message
   - add the `_dispatch_action` branch
4. **REFACTOR** — if the slack/discord paths share shape, extract a small
   `_send_to_integration(...)` helper.

## 5. Edge Cases & Error Handling

- `health.tags` `NULL` → `[]`; duplicate tag → idempotent success (no-op)
- 21st tag → loud `ok: False`, row unchanged
- Slack/Discord senders raise → `ok: False`, run continues
- No integration connected → loud, specific reason (never silent success)
- `message` missing → `ok: False`
- Mid-run DB error → rollback + `ok: False` (session usable for sibling actions)
