### Phase 3 — `create_task` / `schedule_task` handlers

**Goal:** both actions persist tasks from the playbook engine.

**Files:**
- `src/services/playbook_engine.py` (modify)
- `tests/test_playbook_task_actions.py` (create)

**Steps:**
1. **RED** — `tests/test_playbook_task_actions.py` (own builders copied from
   `test_playbook_engine.py:56-132`; playbook with
   `[{"type": "create_task", "config": {"description": "Follow-up", "due_in_days": 3,
   "priority": "high"}}]`):
   - AC1: row persisted (org, email, description, due, priority, status `open`,
     `playbook_execution_id` set); result `{task_id, description, due_at}`
   - AC2: `due_in_days: 3` → `due_at` ≈ now+3d; no due config → `due_at NULL`
   - AC3: explicit `due_at` beats `due_in_days`
   - AC4: `schedule_task` accepted without `priority` (defaults `medium`); invalid
     priority → `ok: False`
   - AC5: missing/empty description → `ok: False`
   - AC6: failing task action doesn't block siblings
2. **GREEN** — implement in `playbook_engine.py`:
   - shared `_persist_task(config, customer_email, health, db, allow_priority=True)`
   - `_handle_create_task` and `_handle_schedule_task` (schedule_task passes
     `allow_priority=False` → priority forced `medium`; an explicit `priority` in a
     schedule_task config is refused loudly — honest config, no silent ignore)
   - `due_at` resolution: `config.get("due_at")` (parse ISO, validate) else
     `utcnow() + timedelta(days=int(due_in_days))` when `due_in_days` present else `None`
   - `_dispatch_action` branches for both types
   - wrap persistence in `try/except` → rollback + `ok: False` (session usable)
3. **REFACTOR** — only if the two handlers share >80% shape.

**Validation:** `pytest tests/test_playbook_task_actions.py tests/test_playbook_engine.py -q`
**Commit:** `feat(playbook-tasks): create_task + schedule_task playbook actions (TDD)`

## 5. Edge Cases & Error Handling

- `due_in_days: 0` → `due_at = now` (accepted)
- invalid ISO `due_at`, negative `due_in_days`, invalid priority, missing description →
  `ok: False` with reason
- duplicate/identical task descriptions are **not** deduped (each run is a new task —
  the rate-limiter on executions is the guard)
- DB failure mid-insert → rollback, `ok: False`, siblings continue
