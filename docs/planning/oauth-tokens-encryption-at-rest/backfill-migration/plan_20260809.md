### Phase 2: GREEN — the migration

**Goal:** the migration module passes the Phase 1 tests; `alembic heads` stays single.

**Prerequisites:** Phase 1 RED committed.

**Files to create:**
- `services/backend-api/alembic/versions/<new_rev>_encrypt_integration_oauth_tokens.py`

**Implementation steps:**
1. Revision id: pick a short readable id in the repo's style (e.g. `c7d8e9f0a1b2`). `down_revision = "a9b8c7d6e5f4"`. **No trailing comment on `down_revision`** (the false-fork trap, `d5e6f7a8b9c0:24`).
2. `upgrade()`:
   ```python
   import os
   import sqlalchemy as sa

   def upgrade() -> None:
       key = os.environ.get("LLM_ENCRYPTION_KEY")
       if not key:
           raise RuntimeError(
               "LLM_ENCRYPTION_KEY is not set; refusing to leave OAuth tokens in "
               "plaintext. Generate a Fernet key (e.g. python -c \"from cryptography.fernet "
               "import Fernet; print(Fernet.generate_key().decode())\"), set "
               "LLM_ENCRYPTION_KEY, and re-run `alembic upgrade head`."
           )
       from cryptography.fernet import Fernet
       fernet = Fernet(key.encode())
       conn = op.get_bind()
       rows = conn.execute(
           sa.text(
               "SELECT id, oauth_access_token FROM integrations "
               "WHERE oauth_access_token IS NOT NULL AND oauth_access_token != ''"
           )
       ).fetchall()
       for row_id, token in rows:
           if token.startswith("gAAAAA"):
               continue  # already Fernet ciphertext — never double-encrypt
           conn.execute(
               sa.text("UPDATE integrations SET oauth_access_token = :enc WHERE id = :id"),
               {"enc": fernet.encrypt(token.encode()).decode(), "id": row_id},
           )
   ```
   - Docstring must state: online-only (no `--sql` support), fail-closed by design (decision 2026-08-09), idempotent via the `gAAAAA` prefix skip, and that the runtime fix ships in the same branch so post-deploy writes are already ciphertext.
3. `downgrade()`: best-effort decrypt back to plaintext, `except (ValueError, InvalidToken): pass` per row (mirror `h1i2j3k4l5m6:194-224`); missing key → skip rows (cannot decrypt), do not raise — downgrade is best-effort by convention.
4. Run the Phase 1 tests — **GREEN**. Then `alembic heads` (from `services/backend-api` with the env exported) — exactly one head, the new revision.

## Testing Strategy

- The sqlite-based migration test (Phase 1) is the full test surface: encrypted in place, skip already-encrypted, fail-closed on missing key, downgrade round-trip, NULL/empty untouched.
- CI: clean-DB `alembic upgrade head` with the CI dummy key — zero rows, fast path.
- Do not attempt offline/`--sql` — the migration uses `op.get_bind()` (repo-wide backfill convention).

## Environment & Secrets

- `LLM_ENCRYPTION_KEY` is required at migration time in production: the Dockerfile runs `python -m alembic upgrade head` in-container before uvicorn with the compose-injected key (`docker-compose.prod.yml:79`). CI sets a dummy key (`ci.yml:56`).
- `alembic/env.py` does **not** `load_dotenv()` — locally, export `DATABASE_URL` and `LLM_ENCRYPTION_KEY` before `alembic upgrade head`.
- Consequence (documented in `docs-and-tracking` aspect): installs that never set `LLM_ENCRYPTION_KEY` get a hard abort on deploy with an actionable message — intended behavior.

## Edge Cases & Error Handling

- Missing key → `RuntimeError` with generate-key instructions (never the `h1i2j3k4l5m6:148` "store as-is" fallback).
- Already-ciphertext rows (written by the fixed runtime after deploy, or a re-run) → skipped via `gAAAAA` prefix.
- NULL / empty-string rows → untouched by the SELECT predicate.
- Downgrade with missing key or corrupt value → best-effort skip, no raise.
- Offline `--sql` mode → unsupported, stated in the docstring.
