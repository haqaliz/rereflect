## 2. Implementation Phases

### Phase 1: Renderer (TDD)

- **Goal:** `render_scheduled_report_email(report) -> {subject, html}`.
- **Steps:**
  1. RED: `tests/test_scheduled_report_email.py` — subject format
     `[<org name>] <Type label> report (<range label>)`; html contains title, narrative
     (when present), one table/list per section for both `data.type == "table"` and
     `"series"` shapes, footer links to `{APP_URL}/reports` and `/settings/notifications`,
     and the honest "view the full report for charts" note; a section with unknown data
     shape renders a fallback without raising.
  2. GREEN: implement renderer; type/range label maps (spec §2.3). Use the worker's
     `src/services/` directory convention (check an existing service file for import style).
- **Validation:** `cd services/worker-service && pytest tests/test_scheduled_report_email.py -v`.
- **Commit:** `feat(worker): scheduled report email renderer (TDD)`

### Phase 2: Sender (TDD)

- **Goal:** `send_scheduled_report_email(to_email, organization_name, subject, html) -> bool`
  in `src/email.py`, delegating to the existing raw `_send_email` (skips when no key).
- **Steps:**
  1. RED: monkeypatch `src.email.requests.post` — no key (`RESEND_API_KEY=None` via
     monkeypatch of the module constant) → returns False, `requests.post` never called;
     key set + mocked 200 → True, payload has `to`/`subject`/`html`; mocked 5xx → False.
  2. GREEN: add the function; follow `send_weekly_digest_email`'s placement/style but use
     `_send_email` directly (no template).
- **Validation:** targeted pytest; then full worker suite.
- **Commit:** `feat(worker): send_scheduled_report_email via BYOK Resend (TDD)`

## 6. Edge Cases & Error Handling

- HTML escaping: escape section text values (report content is user-derived feedback —
  escape `&<>"'`) — add a test with a malicious string.
- Long emails/subjects: cap subject length (~150 chars) defensively.
- Narrative `None` → renderer omits the narrative block (no "None" text).
