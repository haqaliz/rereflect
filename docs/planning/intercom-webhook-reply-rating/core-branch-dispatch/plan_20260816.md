## 1. Placement decisions (pinned)

### 1.1 The guard sits at the TOP of `_process_event_for_source`, before the trigger check

Insert **immediately after the slack channel-match block** (`source_events.py:290-294`)
and **before `# Check triggers` (:296)**. An intercom replied/rating event must never
reach `adapter.check_triggers` (:298) or `adapter.get_external_ids` → dedup (:309-319).

Add a module-level constant near the top of `source_events.py`:

```python
# Intercom events routed to the webhook enrichment branch (PRD R1) instead of
# the trigger/dedup/create flow. The `enriched` status logged here is NEW
# vocabulary: it is never dedup-relevant (the dedup filter below matches only
# processed/pending) and never blocks a later `created` delivery.
INTERCOM_WEBHOOK_ENRICH_EVENTS = ("conversation.user.replied", "conversation.rating.added")
```

Guard body (pinned shape — do not re-derive):

```python
    # Intercom replied/rating events bypass trigger + dedup: route straight into
    # the webhook enrichment module. Enrichment is NOT trigger-gated and NEVER
    # creates items — it merges into the conversation's existing FeedbackItem, or
    # logs a noop/ignored row (the create path owns item creation).
    if source.source_type == "intercom" and event_type in INTERCOM_WEBHOOK_ENRICH_EVENTS:
        # Lazy import — house convention (analysis.py:156, source_events.py:389).
        # Plain import, never a swallowed-`except` import (import-sweep guard).
        from src.services.intercom_webhook_enrich import enrich_webhook_item

        result = enrich_webhook_item(db, source, event_type, event_data)
        outcome = result["status"]
        conv_id = ((event_data.get("data") or {}).get("item") or {}).get("id")

        if outcome == "enriched":
            _log_event(
                db, source_id, org_id, external_event_id, event_type,
                event_data, "enriched", None,
                feedback_id=result.get("feedback_id"),
                message_id=conv_id,
            )
        elif outcome.startswith("noop"):
            _log_event(
                db, source_id, org_id, external_event_id, event_type,
                event_data, "ignored", None, message_id=conv_id,
            )
        else:  # "error/auth_error" and any unexpected module status
            event_log = _log_event(
                db, source_id, org_id, external_event_id, event_type,
                event_data, "failed", None, message_id=conv_id,
            )
            event_log.error_message = outcome

        return {
            "source_id": source_id,
            "status": outcome,
            "changed": result.get("changed", False),
            "feedback_id": result.get("feedback_id"),
        }
```

**Status vocabulary — pinned** (spec open question, resolved here):

| Module outcome | Logged status | error_message | Rationale |
|---|---|---|---|
| `enriched` | `enriched` (+ `feedback_id`) | — | New vocabulary; dedup-safe; never blocks a later `created` delivery |
| `noop/no_item`, `noop/not_found`, any `noop/*` | `ignored` | — | Deliberate no-op (nothing to merge); not a delivery failure |
| `error/auth_error` (and any other module status) | `failed` | the raw outcome string | **Pinned: `failed`, not `ignored`.** A 401/403 delivery is a real failure that must be visible in the audit log. `failed` is already in the model's comment vocabulary (models/__init__.py:281) — no schema change. `ignored` is reserved for deliberate no-ops. Both `failed` and `ignored` are outside the dedup filter's `(processed, pending)` set, so neither is dedup-relevant. |

- `trigger_matched` is `None` for all three (the trigger check never ran).
- `external_event_id` and `event_type` pass through unchanged.
- `_log_event`'s `processed_at` guard (`:480`, currently `status in ["processed", "ignored"]`)
  is extended to `status in {"processed", "ignored", "enriched", "failed"}` so terminal
  enrichment outcomes carry a `processed_at` in the audit row. One-line change; no test
  asserts the current behavior (verified: no worker test references `processed_at`).
- **`IntercomTransientError` is NOT caught here.** The module raises it on 429/5xx; it
  propagates out of `_process_event_for_source` to `process_source_event`'s existing
  `except Exception` (`:116-119`) → `db.rollback()` + `self.retry`. **No partial commit:
  no FeedbackSourceEvent row survives a transient** (a `failed` row is only committed for
  the auth_error *return value*, never for a re-raised transient).

### 1.2 Return-dict shape + how `process_source_event` collects changed ids

- `_process_event_for_source` enrichment branch returns
  `{"source_id", "status": <module outcome>, "changed": bool, "feedback_id": int|None}`
  (§1.1, pinned). This is the ONLY new return shape; the create/pending paths are untouched.
- In `process_source_event`, **after** the `for source in sources:` loop (`:94-103`) and
  **before** `db.commit()` (`:105`):

  ```python
              changed_feedback_ids = list(dict.fromkeys(
                  r["feedback_id"] for r in results
                  if r.get("changed") and r.get("feedback_id")
              ))
  ```

  `dict.fromkeys` preserves order and collapses duplicates (one webhook delivery may
  match several FeedbackSources for the same org+conversation). The created path's result
  dict has no `changed` key → never collected. `process_source_event`'s return shape is
  unchanged (`{"status": "processed", "results": results}`).

### 1.3 Post-commit dispatch — exactly between cache invalidation and the return

Insert **between** the cache-invalidation block (`:107-112`) and `return` (`:114`) —
i.e. after `db.commit()` (`:105`) AND after `cache_invalidate` (`:107-112`), mirroring
the pull's guarded post-commit pattern (`intercom_sync.py:388` commit → `:397-406`
guarded loop):

```python
            # Re-analysis dispatch — strictly AFTER the end-commit (:105) + cache
            # invalidation. reanalyze_feedback commits itself (analysis.py:299), so
            # calling it before the core commit would re-analyze stale text (PRD R4;
            # pull precedent intercom_sync.py:388 -> :397-406). Guarded per item so a
            # seam failure can never break the delivery — the seam's own task retries.
            from src.tasks.analysis import reanalyze_feedback

            for feedback_id in changed_feedback_ids:
                try:
                    reanalyze_feedback(db, feedback_id)
                except Exception:
                    logger.exception(
                        "Intercom webhook enrichment: re-analysis dispatch failed for "
                        "feedback %s (event %s)",
                        feedback_id,
                        external_event_id,
                    )
```

- Never call `reanalyze_feedback` before `:105`. Never inside `_process_event_for_source`.
- The `from src.tasks.analysis import reanalyze_feedback` is call-time (so tests patch
  `src.tasks.analysis.reanalyze_feedback` and the call resolves the patch — the same
  technique the pull dispatch tests use).
- **Never-raise on seam failure**: the per-item `try/except Exception` logs and continues.

### 1.4 `enriched` status is new vocabulary — model comment + core docstring

- `src/models/__init__.py:281` — the status column comment becomes:

  ```python
  status = Column(String(20), nullable=False, default='pending')  # pending, processed, ignored, failed, enriched — enriched is never dedup-relevant (dedup matches only processed/pending; it never blocks a later `created` delivery)
  ```

- `source_events.py` — the `process_source_event` docstring (`:49-68`) gains one note:

## 7. Edge Cases & Error Handling

| Case | Required behaviour |
|---|---|
| Replied/rating with **no existing item** (incl. out-of-order reply-before-created) | Module returns `noop/no_item` → logged `ignored` (message_id = conv id), no item, no dispatch; a later `created` delivery is **not** dedup-blocked (the `enriched`/`ignored` statuses are outside `(processed, pending)`) |
| **Redelivery** of the same reply | part_id membership → `changed=False` → no text change, no metadata change, no second dispatch |
| **Rating-only** change | metadata updated, `changed=False` → no re-analysis |
| `error/auth_error` (401/403) | Logged `failed` + `error_message`, no retry, no item change (module returns it as a value; the guard never raises on it) |
| 429/5xx / network (transient) | Module raises `IntercomTransientError` → propagates to `:116-119` → rollback + `self.retry`; **no partial commit** (no event row survives) |
| Unexpected module status string | Default branch → logged `failed` with `error_message = outcome` (defensive) |
| Multiple matching sources for one delivery | `changed_feedback_ids` deduped via `dict.fromkeys` → one dispatch per item id |
| Seam failure on dispatch (`reanalyze_feedback` raises) | Per-item `try/except Exception` logs via `logger.exception` and continues; delivery result is unaffected |
| Other source types / other event types | Guard `source.source_type == "intercom" and event_type in (...)` → not taken; create/pending paths byte-identical |
