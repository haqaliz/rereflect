## 4. Testing Strategy

**Unit / seam (worker)** — pure extraction against the pinned envelopes:
`extract_reply_parts` yields exactly one comment part (id/author/body/created_at), the
first message is excluded, the null rating yields `None`; `extract_rating` yields
`{rating, remark, rated_at}`; the conversation-id key path
(`event_data["data"]["item"]["id"]`) is pinned as the enrichment module's input contract.

**Integration (backend route)** — POST each fixture through
`/api/v1/webhooks/intercom/events` with `queue_source_event` patched; assert the **full
kwargs** (`external_event_id == item.id == conversation id`, `event_data == envelope`,
`provider_context = {conversation_id, workspace_id}`) via `assert_called_once_with`.

**Contract (cross-service)** — the two new fixtures are read by BOTH suites through
raise-if-missing loaders (`AssertionError`, never skip). The worker pins "this envelope
parses to the reply/rating the merge consumes"; the backend pins "this envelope is what
the route queues". Neither service can import the other; the shared files are the only
common artifact — exactly the envelope-seam-fix contract, extended to reply/rating.

## 8. Ambiguities flagged (for the reviewer)

1. **Route tests rewritten to POST the fixtures** (vs keeping inline payloads and only
   adding assertions). Chosen: fixture-backed POSTs, because it makes the backend suite
   genuinely "read both new fixtures" (AC1) and pins `event_data == the shared file` —
   the same treatment the created contract test already applies. Alternative
   (inline + assertions) is weaker: it would not read the fixtures and would pin a shape
   the worker never sees.
2. **`conversation_rating: null` in the reply fixture** — chosen explicit `null`
   (real API is nullable). A missing key is equivalent to `null` for `extract_rating`
   (both → `None`); if a reviewer prefers omission for minimalism, either is valid — the
   pin (`extract_rating → None`) is identical.
3. **Rating fixture omits `conversation_parts`** — chosen to pin the "payload without
   parts" fallback case. The alternative (empty wrapper `{"conversation_parts": []}`)
   parses to the same `[]`; omission is closer to "absent → fallback fetch".
4. **RED label semantics** — these are GREEN-on-arrival contract pins (production already
   correct); the only genuine RED is the loader's raise-if-missing guard, proven by the
   Phase 2 RED probe. The `test(worker)/test(api): RED` commit prefixes follow house
   style for test-first work; no production GREEN commit exists because nothing was broken.
5. **Two contract tests vs two route pins** — the backend side both reads the fixtures
   (contract class: `event_data == envelope`) and pins the full kwargs (route tests:
   external_event_id/event_data/provider_context). Slight overlap is deliberate — the
   contract class is the cross-service seam; the route tests pin the queue call exactly.
