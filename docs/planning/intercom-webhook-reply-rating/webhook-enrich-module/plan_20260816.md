## 0. Scope recap

A new worker service-layer module that turns a `conversation.user.replied` /
`conversation.rating.added` webhook event into a **merge into the existing
per-conversation FeedbackItem**, returning a status dict the core branch dispatches on.

- **Never creates items.** Strictly merge-into-existing (PRD D3 invariant).
- **Never touches `customer_email`.** (admin/bot rule — adapter contract, #16 semantics verbatim).
- **Never commits, never dispatches re-analysis.** The caller owns the transaction and the
  post-commit dispatch (house rule — `_enrich_conversation_replies` only mutates the item;
  R4 belongs to `core-branch-dispatch`).
- **No new dependencies, no migration, no plan gate** (`SELF_HOSTED=true`).

## 1. Pinned contract (the deliverable)

### 1.1 Module + function

- **File:** `services/worker-service/src/services/intercom_webhook_enrich.py`
- **Function:**
  ```python
  def enrich_webhook_item(db, source, event_type, event_data) -> dict
  ```
  - `db` — SQLAlchemy session (caller owns the transaction).
  - `source` — a `FeedbackSource` row (`organization_id`, `id`, `source_type`).
  - `event_type` — one of `"conversation.user.replied"` / `"conversation.rating.added"`
    (accepted for parity with the pinned signature; both map to the same merge, so the
    module does not branch on it beyond logging).
  - `event_data` — the full webhook envelope (the conversation-wrapped shape).

### 1.2 Status-dict contract

`{"status": str, "changed": bool, "feedback_id": int | None}` with EXACTLY these values:

| Branch | `status` | `changed` | `feedback_id` |
|---|---|---|---|
| Item exists, merge ran (payload-first **or** fallback), anything merged | `enriched` | `True` iff `item.text` changed (new reply parts); rating-only → `False` | `item.id` |
| Item exists, merge ran, **nothing** to merge (idempotent re-delivery / fallback 200 with no parts) | `enriched` | `False` | `item.id` |
| Conversation id missing / unparseable from payload | `noop/no_item` | `False` | `None` |
| No `FeedbackItem` for (org, `source="intercom"`, `source_external_id==conversation_id`) | `noop/no_item` | `False` | `None` |
| Fallback `get_conversation` → 404 (`IntercomNotFoundError`) | `noop/not_found` | `False` | `None` |
| Fallback `get_conversation` → 401/403 (`IntercomAuthError`) | `error/auth_error` | `False` | `None` |
| No Intercom connection row resolvable for the org | `error/no_connection` | `False` | `None` |
| Token decrypt failure (missing `LLM_ENCRYPTION_KEY` / `InvalidToken`) | `error/auth_error` | `False` | `None` |
| Fallback `get_conversation` → 429/5xx/network (`IntercomTransientError`) | — | — | **raises** `IntercomTransientError` (task retry) |

Notes:
- `"noop/not_found"` ≠ `"noop/no_item"`: `not_found` means the *conversation* is gone at
  Intercom; `no_item` means Rereflect has no item for it. The core maps both to
  `ignored`; they are distinct only for auditability.
- `error/no_connection` and the decrypt-failure→`error/auth_error` mapping are **decisions
  made in this plan** (the spec names only `error/auth_error` and allows `|...`). See §8
  ambiguities A2/A3. The core-branch aspect maps every `error/*` uniformly.
- `IntercomTransientError` is the **only** exception that escapes (deliberate — the task's
  retry path). Every other branch returns a dict. No swallowed-`except` anywhere.

## 2. Step-by-step algorithm (pinned)

`enrich_webhook_item`:

1. **Conversation id** — `event_data["data"]["item"]["id"]`. Defensive extraction:
   `item = event_data["data"]["item"]; conversation_id = item.get("id")`. If the lookup
   raises `KeyError`/`TypeError`/`AttributeError`, or `conversation_id` is falsy →
   `{"status": "noop/no_item", "changed": False, "feedback_id": None}` (logged at WARNING,
   never a crash — the core logs `ignored`). The `created` topic is **not** handled here
   (core only routes replied/rating).
2. **Item lookup** — the #16 shape verbatim (intercom_sync.py:268-276), served by the
   `ix_feedback_items_org_source_external` index (feedback.py:85):
   ```python
   from src.models import FeedbackItem
   item_row = (
       db.query(FeedbackItem)
       .filter(
           FeedbackItem.organization_id == source.organization_id,
           FeedbackItem.source == "intercom",
           FeedbackItem.source_external_id == conversation_id,
       )
       .first()
   )
   if item_row is None:
       return {"status": "noop/no_item", "changed": False, "feedback_id": None}
   ```
3. **Payload-first extraction** — `extract_reply_parts(item)` / `extract_rating(item)`
   against the payload's `data.item` (intercom_parts.py tolerates the
   `conversation_parts.conversation_parts[]` dict wrapper and the bare array, so the
   real conversation-wrapped payload works unchanged). If `not parts and not rating`
   (exactly the pull's test, intercom_sync.py:254) →
4. **Fallback** — single `get_conversation(conversation_id)` (helper below). Re-extract
   from the fetched conversation. Error mapping per §1.2.
5. **Merge** — `changed = _enrich_conversation_replies(db, item_row, parts, rating)`
   (lazy import; idempotent by `part_id`; rating metadata-only; never touches
   `customer_email`).
6. **Return** — `{"status": "enriched", "changed": changed, "feedback_id": item_row.id}`.

### 2.1 Fallback helper (module-private)

```python
def _resolve_connection(db, org_id):  # mirrors intercom_writeback._resolve_connection
    # token-paste IntercomIntegration (org-scoped, no workspace match) FIRST,
    # then legacy OAuth Integration(type=="intercom", is_active). Returns
    # (connection, "token_paste"|"oauth") or (None, None).
```

`_decrypt` — the house-local copy (verbatim from intercom_sync.py:82-88 /
intercom_writeback.py:64-70; never import backend `src.utils.encryption`).

```python
def _fetch_conversation(db, source, conversation_id):  # -> (conversation|None, status|None)
    connection, kind = _resolve_connection(db, source.organization_id)
    if connection is None:
        return None, "error/no_connection"
    token_column = (connection.access_token if kind == "token_paste"
                    else connection.oauth_access_token)
    try:
        token = _decrypt(token_column)
    except (ValueError, InvalidToken) as exc:          # non-transient config
        logger.error(...)                              # token never logged
        return None, "error/auth_error"
    from src.clients.intercom import (                 # LAZY (see §2.2)
        IntercomClient, IntercomAuthError, IntercomNotFoundError,
    )
    try:
        with IntercomClient(token) as client:
            return client.get_conversation(conversation_id), None
    except IntercomNotFoundError as exc:
        logger.info("intercom_webhook_enrich: conversation %s gone: %s", conversation_id, exc)
        return None, "noop/not_found"
    except IntercomAuthError as exc:
        logger.warning("intercom_webhook_enrich: auth error org=%s: %s",
                       source.organization_id, exc)
        return None, "error/auth_error"
    # IntercomTransientError is NOT caught here — it propagates for task retry.
```

### 2.2 Import discipline (house convention, sweep-safe)

- **Module-level:** pure `intercom_parts.py` only —
  `from src.adapters.intercom_parts import extract_reply_parts, extract_rating`.
- **Lazy (inside functions):** `src.tasks.intercom_sync._enrich_conversation_replies`,
  `src.clients.intercom.{IntercomClient, IntercomAuthError, IntercomNotFoundError}`,
  `src.models.FeedbackItem`, `src.models.{Integration, IntercomIntegration}`.
- **Never** a swallowed-`except` import. A bare `except Exception` around an import here
  would be a defect on sight (automations-delivery-integrity rule).
- The module imports **no backend-only path** (`src.api`, `src.utils`,
  `src.services.automation_engine`, `src.services.health_score_service`,
  `src.models.feedback_workflow_event`) — `test_worker_import_sweep.py` scans every
  `src/*.py` including this new file, so it must pass unchanged.

### 2.3 Client injection mechanism (test seam)

Because `IntercomClient` is imported **lazily inside `_fetch_conversation`** (per spec),
the injectable-client seam is: tests monkeypatch the **real attribute**
`src.clients.intercom.IntercomClient` (a `from X import Y` resolves `Y` at call time).
`patch.object(intercom_webhook_enrich, "IntercomClient", ...)` would **not** work — the
lazy import rebinds the real class. Pin this explicitly in the test module docstring so a
future contributor does not "fix" it into a module-level import that breaks the seam.

Tests provide a fake client shaped like writeback's `_make_mock_client` — a `MagicMock`
with `__enter__`/`__exit__` returning `self`/`False` and a `get_conversation` fed by a
conversation-id → payload map (the `_fake_client_with_parts` idiom, test_intercom_sync.py:201).

## 7. Edge cases & error handling

- **Out-of-order delivery** (reply webhook before `created`): no item → `noop/no_item`
  → core logs `ignored`; the later `created` delivery is unaffected (this is
  `core-branch-dispatch`'s `enriched`-vs-`processed` pin, not this module's job).
- **Malformed envelope** (no `data.item.id`): `noop/no_item`, never a crash, never a
  client call (no conversation id to fetch).
- **Payload with parts but no rating / rating but no parts**: payload-first satisfies the
  extraction; no fallback (matches the pull's `not parts and not rating` gate).
- **Fallback 200 with no parts**: `enriched`, `changed False` — an idempotent redelivery
  on an existing item, not an error and not a new status (see ambiguity A4).
- **Duplicate `part_id` within one payload**: `_enrich_conversation_replies` collapses
  duplicates (intercom_sync.py:133-139) — merged once (inherited, covered by #16 tests).
- **Token safety (R3)**: the decrypted token is never logged; log messages use
  org_id / conversation_id only.
- **Transaction**: the module mutates `item_row` in place and returns; it never calls
  `db.commit()` / `db.flush()` / `reanalyze_feedback` (the caller's end-commit + R4
  post-commit dispatch).

## 8. Ambiguities & decisions (flag for review)

- **A1 — Credential source for the fallback client.** The spec pins the signature
  `enrich_webhook_item(db, source, event_type, event_data)` and lazy-imported
  `IntercomClient`, but is silent on where the access token comes from. **Decision:**
  org-scoped, token-paste `IntercomIntegration` first, then legacy OAuth
  `Integration` — mirroring `intercom_writeback._resolve_connection`, i.e. the **same
  credential the pull uses**, so the fallback sees exactly what the pull would.
  (Alternative rejected: `source.integration_id` → the OAuth-shaped row only — the
  envelope-seam source fixture points there, but token-paste is the primary Intercom
  install in production.)
- **A2 — No-connection branch.** Spec's status set names `error/auth_error` only.
  **Decision:** `error/no_connection` (allowed by the `|...` in the contract) for the
  "no Intercom connection row" case. In practice nearly unreachable (an intercom source
  implies an integration row), but never raise on it. Core maps every `error/*`
  uniformly — confirm the core-branch plan reads any `error/...` prefix.
- **A3 — Decrypt failure → `error/auth_error`.** Missing `LLM_ENCRYPTION_KEY` /
  `InvalidToken` are non-transient, operator-recoverable config errors (writeback R6),
  so they map to `error/auth_error` (no retry) rather than raising. This stretches
  `auth_error` beyond a literal 401/403 — accepted, flagged.
- **A4 — "Nothing to merge" is not a new status.** When the item exists and the merge
  runs but finds nothing new (idempotent re-delivery, or fallback 200 with no parts),
  the module returns `enriched` with `changed=False`. The spec's status set has no
  `noop/no_content`; inventing one would force the core into vocabulary it did not plan
  for. `enriched/changed=False` is exactly the AC2 redelivery semantic.
- **A5 — Injection seam location.** Because `IntercomClient` is lazy-imported inside
  `_fetch_conversation`, tests must patch `src.clients.intercom.IntercomClient` (resolved
  at call time), **not** the module attribute. Documented in the test docstring so the
  seam survives "refactors" to module-level imports.
- **A6 — Missing-id handling.** Spec pins extraction at step 1 but not the absent-id
  branch; `noop/no_item` chosen (never raise, never fetch, core logs `ignored`).
- **A7 — Event-type values.** The two routed topics are `conversation.user.replied` and
  `conversation.rating.added` (PRD R1). The module accepts `event_type` for signature
  parity and logs it but does not branch; topic-gating happens in `core-branch-dispatch`.
  The `created` topic is out of scope here.
